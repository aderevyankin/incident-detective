# incident-detective — скилл разбора инцидентов

Скилл разбирает баги и инциденты на стендах: собирает логи, ищет похожее в базе знаний,
находит место в коде и честно оценивает, насколько выводу можно верить — вместо того чтобы
пересказывать сырые логи или гадать по одной строке трейсбека.

Формат — [Agent Skills](https://qwenlm.github.io/qwen-code-docs/en/users/features/skills/):
папка со `SKILL.md`, YAML-фронтматтером и вспомогательными файлами. Формат общий для
нескольких агентных CLI, поэтому скилл переносим по замыслу — какие платформы сегодня
проверены на практике, см. раздел «[Поддерживаемые платформы](#поддерживаемые-платформы)»
ниже; ссылка на документацию формата выше ведёт на описание Qwen Code как одной из
реализаций, а не как единственно возможной.

Показать проект за десять минут: [`docs/presentation.html`](docs/presentation.html) — один файл, открывается в браузере без сети и сборки.

## Быстрый старт

Отдельного установщика нет — скилл ставится копированием. Клонируй этот репозиторий
(или возьми его выгрузку) — либо просто дай ссылку на репозиторий своему AI-ассистенту
и попроси поставить скилл, он проделает те же шаги.

<!-- check-docs: skip (копирует в домашнюю директорию — не для автоматической
     проверки) -->

```bash
cp -R incident-detective ~/.qwen/skills/incident-detective   # личный скилл
cp -R incident-detective .qwen/skills/incident-detective     # проектный: едет в git с командой
```

Дальше:

1. Перезапусти CLI — скиллы читаются при старте.
2. Проверь, что скилл виден: `/skills`.
3. Опиши инцидент своими словами — скилл включается сам (см. «Как включается» ниже).

**Обновление поверх существующей установки** — то же копирование, но с оговоркой:
записи базы знаний внутри директории скилла (`kb/INC-*.md`) при перезаписи затираются,
автоматически их никто не спасает. Перед обновлением вынеси записи `INC-*.md` в
сторону и верни после, пересобрав индекс (`kb_index.py`), — или держи базу снаружи,
через `INCIDENT_KB_DIR` либо `memory/knowledgebase/` в проекте (см. «База знаний»
ниже): вынесенную базу обновление не трогает вовсе.

## Как это выглядит

Коротко: пользователь описывает симптом, скилл сам заводит план, разбирает логи,
проверяет базу знаний и код, и отвечает с явным уровнем уверенности — не выдавая гипотезу
за установленный факт.

> **Пользователь:** В логах payment-api на stage вылетает таймаут, оплаты не проходят.
> Вот файл: `payment.log`.
>
> **Скилл:** нашёл 1 повторяющийся шаблон ошибки (`ConnectionTimeoutError`, пул
> соединений), похожий инцидент двухнедельной давности с той же сигнатурой и место в
> коде, где класс исключения объявлен и выбрасывается. Уровень — **гипотеза** (0.39):
> совпадений три из четырёх контуров, но ни одно не подтверждено окончательно. Предлагаю
> завести задачу на доисследование, а не чинить вслепую.

Это сокращённая версия настоящего разбора — целиком, со всеми командами и выводом
каждого шага, в [`docs/walkthrough.md`](docs/walkthrough.md). Он проходит на фикстурах
из `tests/fixtures/`, поэтому воспроизводится один в один.

## Режимы запуска

Скилл работает в двух режимах, и разница между ними не в настройках, а в том, есть ли
рядом человек.

**Диалоговый** — по умолчанию, всё описанное выше: скилл спрашивает недостающее
вариантами, показывает текст тикета до создания, предлагает следующий шаг выбором.

**Автономный** — разбор от алерта, без человека в контуре: обвязка (вебхук, cron,
CI-job) получает алерт и запускает клиента одной командой. Включается переменной
`INCIDENT_MODE=auto`. Каждый вопрос в нём заменён правилом вывода: стенд и сервис
берутся из алерта, источник логов — из переданного пути и карты источников, расположение
базы знаний — только из явной настройки. Неопределённость завершает разбор **вердиктом
«данных недостаточно»**, а не догадкой: в разборе, который никто не перечитает, догадка
дороже.

<!-- check-docs: skip (запускает клиента GigaCode и пишет в /srv — команда для
     машины обвязки, а не для воспроизводимой проверки; полный профиль запуска
     с проверкой флагов — в incident-detective/references/aiops.md) -->

```bash
python3 ~/.gigacode/skills/incident-detective/scripts/alert_to_incident.py \
  --file /srv/incident-runs/9f2c1a44b7e0/alert.json \
  > /srv/incident-runs/9f2c1a44b7e0/incident.json

INCIDENT_MODE=auto \
INCIDENT_NOW="2026-07-28 16:20:03" \
INCIDENT_KB_DIR=/srv/incident-kb \
INCIDENT_TRACE_FILE=/srv/incident-runs/9f2c1a44b7e0/calls.log \
INCIDENT_SESSION_FILE=/srv/incident-runs/9f2c1a44b7e0/session.json \
timeout 900 gigacode -p "Разбери инцидент. Карточка: /srv/incident-runs/9f2c1a44b7e0/incident.json. Логи: /var/log/payment-api/. Отчёт положи в /srv/incident-runs/9f2c1a44b7e0/." \
  --session-id 9f2c1a44b7e0 --output-format json --channel CI \
  --max-session-turns 20 --approval-mode default \
  --exclude-tools write_file,edit --allowed-mcp-server-names kibana-mcp \
  --append-system-prompt "Разбор инцидента скиллом incident-detective в автономном режиме." \
  > /srv/incident-runs/9f2c1a44b7e0/session.json
```

Переменные, которые задаёт обвязка: `INCIDENT_MODE=auto` (признак режима),
`INCIDENT_NOW` (без него повторный прогон того же алерта даст другое окно),
`INCIDENT_KB_DIR` (без него разбор идёт, но запись в базу не делается),
`INCIDENT_TRACE_FILE` и `INCIDENT_SESSION_FILE` (телеметрия и поток сессии рядом с
отчётом — по одному файлу прогона находятся остальные).

**На выходе — `/srv/incident-runs/9f2c1a44b7e0/report.json`**: вердикт, уровень
уверенности, сигнатура, доказательства с указанием источника, пройденные и пропущенные
контуры с причинами, судьба записи базы знаний и черновик следующего шага. Отчёт
собирает скрипт, а не формулировка модели: контракт, который держится на форматировании
модели, ломается у потребителя и молча. Состав полей —
[`templates/aiops-report.md`](incident-detective/templates/aiops-report.md).

Отсутствие файла отчёта и вердикт «данных недостаточно» — **разные события**: первое
значит, что прогон не состоялся, второе — что разбор состоялся и честно отказался
делать вывод.

### Граница ответственности

В автономном режиме подтверждать действия некому, и механизма подтверждения запуска
команд у клиента в этом режиме **нет** — это измерено прогоном, а не предположено.
Поэтому запрет изменяющих действий обеспечивает **среда запуска**: изоляция процесса
(sandbox, непривилегированный пользователь, read-only монтирование), сужение перечня
MCP-серверов и исключение инструментов правки. Инструкции скилла здесь второй эшелон, а
не гарантия.

Отсюда условие применения: **на стенде, где изоляции нет, автономный режим не
применяется** — там разбор идёт диалогом. Это осознанное решение, а не недоработка.

Механизмы сужения самого клиента (`--exclude-tools`, `--allowed-mcp-server-names`,
`--sandbox`) прогоном положительной и отрицательной проверки не подтверждены и защитой
не называются. Что проверено запуском, а что описано по документации платформы —
с датой и версией сборки в
[`references/platforms.md`](incident-detective/references/platforms.md), раздел «Режимы
запуска». Правила самого режима — в
[`references/aiops.md`](incident-detective/references/aiops.md): там же таблица «признак
в выводе клиента → что поправить в профиле запуска», рассчитанная и на дежурного, и на
агента.

Обвязка в поставку скилла **не входит**: скилл остаётся директорией, которую копируют,
и демонов с собой не приносит.

## Поддерживаемые платформы

Установка на любой платформе одинакова — копирование `incident-detective/` в её
директорию скиллов:

| Платформа | Директория скиллов | Полный разбор проверен |
|---|---|---|
| GigaCode — целевая | `~/.gigacode/skills/` или `.gigacode/skills/` проекта | нет — см. ниже |
| Qwen Code | `~/.qwen/skills/` или `.qwen/skills/` проекта | да — тесты и `docs/walkthrough.md` гоняются на ней |
| Claude Code и другие CLI с форматом Agent Skills | директория скиллов платформы | нет — см. ниже |

GigaCode устроен в точности как Qwen Code — те же имена инструментов, те же файлы
настроек, — и отличается только корневым каталогом: везде, где у Qwen Code `.qwen/`, у
GigaCode `.gigacode/`. Разработка и проверка идут на Qwen Code, целевая платформа —
GigaCode; при расхождении приоритет у неё.

Раздел честно называет то, что проверено запуском, а не то, что задумано: пока
прогонялась только Qwen Code. Имена инструментов при этом к платформе не привязаны —
`SKILL.md` называет их по назначению («инструмент ведения списка задач», «инструмент
вопроса с вариантами»), а соответствие назначения имени на каждой платформе собрано в
`incident-detective/references/platforms.md`. Обязательность плана работ и вопроса
вариантами от имени инструмента не зависит. Пометка «проверен» снимается результатом
прогона, а не намерением его выполнить: когда разбор прогонят на GigaCode, в таблице
изменится её строка.

При развёртывании скилла сразу в несколько платформ каждая копия несёт свою базу знаний.
Чтобы база была одна на все, задайте `INCIDENT_KB_DIR` — см. «[База
знаний](#база-знаний)».

## Требования к окружению

`python3` версии **3.8 или новее** — только стандартная библиотека, никаких зависимостей
и сетевых вызовов. Для контура кода дополнительно `git`.

Скилл проверяет это сам, первым шагом разбора, и говорит результат в чат — установка
копированием окружение заранее не проверяет, значит проверять обязан сам разбор. Дальше:

- **`git` нет** — контур кода работает по файлам, но без истории коммитов.
- **`python3` нет или он старее 3.8** — скилл сообщает об этом и переходит в
  **ограниченный режим**: база знаний читается как markdown, логи разбираются выборочно
  средствами оболочки. Сводки по шаблонам, хронологии, цепочки запроса и подсчёта
  уверенности в таком разборе нет, поэтому вывод не поднимается выше «гипотезы», и это
  сказано в ответе. Обходить ограничение — подбирать другой интерпретатор, писать парсер
  на ходу — скиллу запрещено: тихо неверный разбор хуже честного «не могу».

Установка интерпретатора условием не выдвигается: там, где скилл нужнее всего, ставить
что-либо обычно нельзя.

Проверить, что скрипты не разъехались с заявленной минимальной версией:

```bash
python3 tools/check_compat.py
```

## Устройство

Разбирает баги и инциденты по трём контурам:

| Контур | Вопрос | Скрипты |
|---|---|---|
| **База знаний** | Мы это уже видели? Откуда брать логи? | `kb_search.py`, `kb_add.py`, `kb_index.py` |
| **Логи** | Что происходило на самом деле? | `parse_logs.py`, `timeline.py`, `trace.py` |
| **Код** | Где ломается и из-за чего? | `code_hints.py` |

В типовом разборе все три контура проходит `triage.py` — одной командой, за один запуск.

Таблица здесь витринная — она же вход в проект для человека. Канон, по которому работает
агент, — та же таблица в [`incident-detective/SKILL.md`](incident-detective/SKILL.md);
расходиться им нельзя, и правится сначала он.

Связывает контуры **сигнатура** — устойчивый отпечаток ошибки (класс исключения,
HTTP-статус, шаблон сообщения). Логи её порождают, база знаний по ней ищет, код по ней
локализуется, новая запись базы её сохраняет. Так разбор второго такого же инцидента
начинается не с нуля, а с готового ответа.

Перед выводом `confidence.py` считает, на скольких контурах он стоит, и переводит это в
уровень: подтверждено данными / вероятная причина / гипотеза. Ни один контур в одиночку
до «подтверждено» не дотягивает — одна опора причину не доказывает.

Разбор не обрывается на выводе: последним шагом скилл предлагает выбором, что делать
дальше — применить правки, завести баг или завести задачу на доисследование. Что
предлагается ведущим вариантом, зависит от того же уровня уверенности: чинить по
гипотезе нечего, а баг с выдуманной причиной хуже честной задачи «разобраться». Тикет
собирается из уже полученного разбора и заводится тем, что есть в окружении (MCP-сервер
трекера, `gh`/`jira`/`linear` в консоли), а если ничего нет — выдаётся готовый текст для
ручного создания. Ни правки, ни тикет не появляются без подтверждения пользователя.

### Как включается

Скилл **самозапускающийся**: включается сам, когда в сообщении есть признак инцидента —
«упало на stage», «504 на проде», «почему падает», вставленный стектрейс, ссылка на
Kibana. Явная команда `/incident-detective` тоже работает, но не нужна.

Первым делом скилл заводит план через инструмент ведения списка задач и дальше строго
ему следует, чтобы не утонуть в логах, забыв спросить базу знаний.

### Про логи

Источников скилл с собой не приносит — он использует то, что уже есть у пользователя.
Порядок фиксированный: сам запрос → карта источников → приложенные данные → перебор
остальных каналов (локальные файлы и каталоги логов проекта, установленные скиллы,
подключённые MCP-инструменты, веб-интерфейсы под учётными данными пользователя). Если не
нашлось ничего — честно просит файл, архив или ссылку. Никаких выводов «по догадке» без
данных.

**Карта источников** — то, чем второй разбор дешевле первого. После успешной выгрузки
скилл записывает, откуда для пары «стенд + сервис» брались логи, каким запросом и как поля
источника ложатся на схему разбора. Записывается и отрицательный результат: источник,
оказавшийся пустым или недоступным, помечается, чтобы следующий разбор туда не ходил.
Запись стареет — не подтверждавшаяся 30 дней выдаётся как требующая проверки, а не как
действующая. Инвентаризация перестаёт выполняться заново каждый раз, а она идёт до первой
строки логов, то есть в самом дорогом месте разбора.

Парсинг полностью локальный и рассчитан на **неструктурированные и разнородные** логи:
формат определяется построчно (JSON, logfmt, syslog, nginx/apache, стектрейсы Java /
Python / Go / JS, произвольный текст), многострочные записи склеиваются, похожие
сообщения схлопываются в шаблоны с частотами. На выходе — сводка на страницу вместо
десятков тысяч строк.

## База знаний

Источник правды — markdown-файлы: читаются человеком, правятся руками, кладутся в git.
`index.json` производный, пересобирается через `kb_index.py`.

### Где она лежит

Расположение — осознанный выбор, а не умолчание: при **первой записи** скилл спрашивает,
где базу держать, и предлагает варианты — в корне проекта (`memory/knowledgebase/`), в
директории скилла (`kb/`) или свой путь. Вопрос задаётся в момент записи, а не в начале
разбора: во время инцидента диалога о хранении не будет. Директория создаётся только
после ответа — молча база не заводится нигде.

Путь разрешается по порядку: флаг `--kb` → `INCIDENT_KB_DIR` → база проекта → `kb/` внутри
скилла. Переменная стоит выше базы проекта — это способ намеренно работать с одной базой из
разных репозиториев. Полное описание порядка со всеми оговорками — канон в
[`references/kb-format.md`](incident-detective/references/kb-format.md), раздел «Где лежит
база».

Выбор закрепляется строкой в профиле оболочки:

```bash
export INCIDENT_KB_DIR=/path/to/team/incidents
```

Для базы в корне проекта строка не обязательна — там выбор читается по наличию
директории; она нужна, чтобы работать с той же базой из других директорий.

**База в репозитории проекта** едет с ним к команде — и записи попадают в git, откуда из
истории не вычищаются. Записи содержат фрагменты логов; решение принимает тот, кто знает
политики проекта.

**База вне скилла обновлением не затрагивается.** Предупреждение о перезаписи при
обновлении копированием (см. «Быстрый старт») касается только базы внутри директории
скилла — вынесенную наружу копирование новой версии не трогает.

## Разработка

### Проверки

<!-- check-docs: skip (self-reference: команда сама запускает tests/run.py, а
     значит и этот же прогон — рекурсия) -->

```
python3 tests/run.py            # весь набор
python3 tests/run.py test_parse # один файл проверок
python3 tests/run.py -v         # подробный вывод
```

Ставить ничего не надо: прогон работает на стандартной библиотеке, как и сам скилл.
Запускается из любой директории. Проверка совместимости с Python 3.8
(`tools/check_compat.py`) и проверка документации (`tools/check_docs.py`) входят в тот
же прогон — точка входа одна. То же самое выполняется в CI на каждый push и pull
request, матрицей `3.8` (минимальная заявленная версия) и `3.12` (современная — на ней
запускает большинство пользователей). Рядом — отдельный job бенчмарка со щадящим
порогом (см. «Про скорость»): его падение не смешивается с падением прогона тестов.

**Что проверяется.** Разбор фикстур с заранее известным ответом: сигнатуры, время
первого события, точка обрыва цепочки. Отсутствие ложных срабатываний — на логе
штатной работы инцидент не находится. Честное «не знаю» — когда контуры не сошлись,
уверенность не поднимается выше гипотезы. Устойчивость ко входу: пустой файл, битая
кодировка, строка чрезмерной длины. Сравнение идёт по JSON-выводу, а не по
markdown: тест не должен падать от переставленного слова в заголовке. Отдельно —
`tools/check_docs.py`: команды из README и `docs/walkthrough.md` действительно
запускаются, перечень capability и дерево файлов в разделе «Структура» совпадают с
репозиторием. Проверка проверяет и саму себя: если извлечение блоков перестало что-либо
находить, прогон падает — «ни одной ошибки» и «ни одной исполненной команды» иначе
выглядят одинаково.

**Что не проверяется.** Поведение модели: самозапуск скилла, порядок шагов разбора,
формулировки вывода. Это инструкции в `SKILL.md`, и проверяются они чтением
спецификации и разбором на живом инциденте, а не запуском скриптов. Скорость —
отдельно, через `tools/bench.py` (не входит в `tests/run.py`: числа зависят от машины,
и гонять их при каждом прогоне — источник ложных падений на медленном железе); в CI
он идёт своим job'ом со щадящим порогом, см. «Про скорость».

**Как меняется ожидаемый результат.** Только вместе с изменением, которое меняет
поведение, и с объяснением, почему новый ответ верен. Если проверка упала при правке,
не предполагавшей смены поведения, — это регрессия, а не устаревший эталон;
переписывать эталон под текущий вывод скрипта нельзя. Режима массовой перезаписи
эталонов нет намеренно: с ним падение теста превращается в однокнопочную
формальность. Обнаружили, что зафиксированный ответ противоречит спецификации, —
это находка: разбирается отдельно, эталон приводится к тому, каким ответ должен
быть по спеке.

Новая фикстура добавляется вместе с файлом в `tests/expected/`: там сказано, что
именно она проверяет и какой ответ считается верным. Фикстуры синтетические — ни
персональных данных, ни секретов, ни внутренних адресов. Набор лежит в публичном
репозитории и заодно служит примером того, что скилл разрешает сохранять.

### Про скорость

Инцидент разбирают тогда, когда что-то лежит, поэтому у скилла есть отдельное
требование — работать быстро, и оно выражено числами, а не пожеланием.

Время съедали не скрипты: они отрабатывают секунды, а разбор занимал минуты, потому что
каждый шаг это отдельный проход модели. Поэтому независимые шаги — база знаний по
сигнатурам, код, уверенность — свёрнуты в один запуск `triage.py`, а типовой разбор
укладывается в пять вызовов инструментов до вывода причины.

Скрипты тоже ускорены — и только так, чтобы результат не изменился (проверяется
сравнением сводок на эталонном входе). Все числа ниже получены `tools/bench.py`:

| Замер | Было | Стало | Бюджет |
|---|---|---|---|
| `parse_logs.py` без фильтров | 35 тыс. строк/с | 55 тыс. | ≥ 50 тыс. |
| `parse_logs.py --level ERROR` | 60 тыс. строк/с | 156 тыс. | ≥ 150 тыс. |
| `parse_logs.py` с окном времени | 63 тыс. строк/с | 372 тыс. | ≥ 150 тыс. |
| вся цепочка `triage.py` | — | 7,5 с | ≤ 15 с |

Главное здесь — отсев записей до полного разбора: раньше фильтры применялись к уже
разобранной записи, то есть девять записей из десяти разбирались, чтобы быть
отброшенными. Плюс сводка ограничена по объёму (12 000 символов): она едет в контекст
агента и остаётся там до конца разбора, а полный результат пишется в файл.

Проверить бюджеты: `python3 tools/bench.py` — генерирует эталонный вход сам, печатает
измеренное рядом с бюджетом и возвращает ненулевой код при нарушении. Не входит в блок
кода намеренно: время выполнения и порог зависят от машины, и `tools/check_docs.py`
проверяет только команды, чей код возврата не зависит от производительности раннера
(см. «Что не проверяется» выше).

Проверяются бюджеты в два яруса. **Строгий прогон** со значениями таблицы — на рабочей
машине, руками, и это пункт приёмки любого изменения, задевающего измеряемые скрипты.
**Щадящий прогон** — в CI отдельным job'ом: `tools/bench.py --budget-scale 5` ослабляет
бюджеты в пять раз (время × 5, скорость ÷ 5) и ловит регрессии на порядок, не флапая
из-за производительности чужого раннера. Множитель задан в
`.github/workflows/checks.yml` с обоснованием по фактическому замеру; таблица бюджетов
при этом остаётся одна — второй, «для CI», нет намеренно.

### Воспроизводимость и отладка

Переменные окружения, все по умолчанию не заданы; без них поведение прежнее.

```bash
export INCIDENT_NOW="2026-07-28 12:00:00"   # «сейчас» для скриптов
```

Задаёт текущее время: год для syslog-записей без года, отсчёт `--since 1h` и `--since
12:30`, дату новой записи базы знаний. Нужна, чтобы чужой разбор воспроизводился на
своей машине и чтобы прогон, прошедший сегодня, не упал в следующем году. Значение,
которое не разбирается как время, — ошибка с сообщением, а не тихий откат на
системные часы.

```bash
export INCIDENT_TRACE_FILE=/tmp/triage-calls.log   # телеметрия вызовов
```

Каждый запущенный скрипт дописывает строку: время, имя, **имена** переданных флагов и
код возврата. Значения аргументов не пишутся — на вход идут фрагменты логов и слова
пользователя, и файл отладки не должен стать ещё одним местом, где они оседают.
В стандартный вывод при этом ничего не добавляется, а недоступный для записи файл
разбор не прерывает.

Смотреть по нему стоит одно: **какие контуры агент реально прогнал**.

```
2026-07-28 12:00:03	parse_logs.py	--format --level	rc=0
2026-07-28 12:00:05	kb_search.py	--from-parsed --format	rc=0
```

Здесь видно, что база знаний спрошена, а `code_hints.py` не запускался — контур кода
пропущен. По тексту ответа агента это не видно: ответ выглядит нормально. Строка с
`rc=0` и отсутствие строки — разные вещи: первое значит, что контур отработал, второе —
что его не запускали.

```bash
export INCIDENT_MODE=auto                          # режим разбора
export INCIDENT_SESSION_FILE=/srv/run/session.json # где обвязка держит поток сессии
```

`INCIDENT_MODE` — признак автономного разбора (см. «Режимы запуска» выше); значение,
отличное от `auto` и `interactive`, — ошибка запуска, а не повод молча выбрать режим.
`INCIDENT_SESSION_FILE` скрипты не пишут — они только называют этот путь в отчёте,
чтобы по одному файлу прогона находились остальные.

### Когда обновлять этот README

Изменение обязано поправить README в своём составе, если оно трогает: установку,
состав скриптов или их флаги, перечень capability, числовые бюджеты, требования к
окружению или границы дозволенного (раздел «Границы» ниже) — правится соответствующий
раздел, и `tools/check_docs.py` проверяет результат в общем прогоне.

Изменение, которое ничего из этого не трогает — например, правит только внутреннее
поведение скрипта, не меняя флагов и вывода, — README не трогает вовсе: раздел не
дописывается «на всякий случай».

Числовой бюджет или замер в README всегда сопровождается тем, чем он получен
(`tools/bench.py`) — число без инструмента измерения не редактируется, оно просто не
попадает в README.

## Границы

Скилл только диагностирует: ничего не рестартует, не деплоит и не правит конфиги на
стендах. Правки в код предлагает, но не применяет молча; тикет во внешнем трекере не
заводит без подтверждения — сначала показывает текст. В базу знаний и в тикеты пишет
шаблоны и сигнатуры, а не сырые дампы; очевидные токены и пароли вычищаются при записи.

Это сжатая версия. Полный перечень границ — канон в
[`incident-detective/SKILL.md`](incident-detective/SKILL.md), раздел «Границы»: его читает
агент во время разбора, и правится он там.
