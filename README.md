# incident-detective — скилл разбора инцидентов для Qwen Code CLI

Скилл в формате [Agent Skills](https://qwenlm.github.io/qwen-code-docs/en/users/features/skills/):
папка со `SKILL.md`, YAML-фронтматтером и вспомогательными файлами. Формат общий для
Qwen Code и других агентов, так что скилл переносим.

Показать проект за десять минут: [`docs/presentation.html`](docs/presentation.html) — один файл, открывается в браузере без сети и сборки.

Разбирает баги и инциденты на стендах по трём контурам:

| Контур | Вопрос | Скрипты |
|---|---|---|
| **База знаний** | Мы это уже видели? | `kb_search.py`, `kb_add.py`, `kb_index.py` |
| **Логи** | Что происходило на самом деле? | `parse_logs.py`, `timeline.py`, `trace.py` |
| **Код** | Где ломается и из-за чего? | `code_hints.py` |

В типовом разборе все три контура проходит `triage.py` — одной командой, за один запуск.

Связывает контуры **сигнатура** — устойчивый отпечаток ошибки (класс исключения,
HTTP-статус, шаблон сообщения). Логи её порождают, база знаний по ней ищет, код по ней
локализуется, новая запись базы её сохраняет. Так разбор второго такого же инцидента
начинается не с нуля, а с готового ответа.

Перед выводом `confidence.py` считает, на скольких контурах он стоит, и переводит это в
уровень: подтверждено данными / вероятная причина / гипотеза. Ни один контур в одиночку
до «подтверждено» не дотягивает — одна опора причину не доказывает.

## Про скорость

Инцидент разбирают тогда, когда что-то лежит, поэтому у скилла есть отдельное
требование — работать быстро, и оно выражено числами, а не пожеланием.

Время съедали не скрипты: они отрабатывают секунды, а разбор занимал минуты, потому что
каждый шаг это отдельный проход модели. Поэтому независимые шаги — база знаний по
сигнатурам, код, уверенность — свёрнуты в один запуск `triage.py`, а типовой разбор
укладывается в пять вызовов инструментов до вывода причины.

Скрипты тоже ускорены — и только так, чтобы результат не изменился (проверяется
сравнением сводок на эталонном входе):

| Замер | Было | Стало | Бюджет |
|---|---|---|---|
| `parse_logs.py` без фильтров | 35 тыс. строк/с | 55 тыс. | ≥ 50 тыс. |
| `parse_logs.py --level ERROR` | 60 тыс. строк/с | 156 тыс. | ≥ 150 тыс. |
| `parse_logs.py` с окном времени | 63 тыс. строк/с | 372 тыс. | ≥ 150 тыс. |
| вся цепочка `triage.py` | — | 7,5 с | ≤ 15 с |

Главное здесь — отсев записей до полного разбора: раньше фильтры применялись к уже
разобранной записи, то есть девять записей из десяти разбирались, чтобы быть
отброшенными. Плюс сводка ограничена по объёму (12 000 символов): она едет в контекст
агента и остаётся там до конца разбора, а полный результат пишется в файл.

Проверить бюджеты: `python3 tools/bench.py` — генерирует эталонный вход сам, печатает
измеренное рядом с бюджетом и возвращает ненулевой код при нарушении.

Разбор не обрывается на выводе: последним шагом скилл предлагает выбором, что делать
дальше — применить правки, завести баг или завести задачу на доисследование. Что
предлагается ведущим вариантом, зависит от того же уровня уверенности: чинить по
гипотезе нечего, а баг с выдуманной причиной хуже честной задачи «разобраться». Тикет
собирается из уже полученного разбора и заводится тем, что есть в окружении (MCP-сервер
трекера, `gh`/`jira`/`linear` в консоли), а если ничего нет — выдаётся готовый текст для
ручного создания. Ни правки, ни тикет не появляются без подтверждения пользователя.

## Установка

```bash
./install.sh              # личный скилл: ~/.qwen/skills/incident-detective
./install.sh --project    # проектный: ./.qwen/skills/incident-detective (едет в git)
./install.sh --yes        # не спрашивать подтверждения на перезапись
./install.sh --help       # справка
```

Затем перезапусти Qwen Code — скиллы читаются при старте. Проверить: `/skills`.

**Переустановка поверх существующей** сначала спрашивает подтверждение. Записи базы
знаний (`kb/INC-*.md`) копируются в резервную папку, её путь печатается, и после
успешного возврата записей папка убирается; если возврат не дошёл до конца — папка
остаётся, и путь к ней уже показан. Новая копия собирается рядом с местом назначения и
подменяет старую переименованием, поэтому сорвавшееся копирование не оставляет систему
без рабочей установки. База, вынесенная наружу через `INCIDENT_KB_DIR`, переустановкой
не затрагивается вовсе.

**Без терминала** — в CI или через конвейер — подтверждение прочитать неоткуда: тогда
переустановка либо получает согласие флагом `--yes`, либо завершается с объяснением.
Неизвестный аргумент установщик тоже не проглатывает: сообщает о нём и показывает справку.

Установщик необязателен: он копирует директорию, сохраняет записи базы знаний и
пересобирает индекс, но скилл работает и при обычном копировании
`incident-detective/` в `~/.qwen/skills/` — в закрытых контурах так чаще всего и бывает.

## Требования к окружению

`python3` версии **3.8 или новее** — только стандартная библиотека, никаких зависимостей
и сетевых вызовов. Для контура кода дополнительно `git`.

Скилл проверяет это сам, первым шагом разбора, и говорит результат в чат — потому что
установщик может и не запускаться. Дальше:

- **`git` нет** — контур кода работает по файлам, но без истории коммитов.
- **`python3` нет или он старее 3.8** — скилл сообщает об этом и переходит в
  **ограниченный режим**: база знаний читается как markdown, логи разбираются выборочно
  средствами оболочки. Сводки по шаблонам, хронологии, цепочки запроса и подсчёта
  уверенности в таком разборе нет, поэтому вывод не поднимается выше «гипотезы», и это
  сказано в ответе. Обходить ограничение — подбирать другой интерпретатор, писать парсер
  на ходу — скиллу запрещено: тихо неверный разбор хуже честного «не могу».

Установка интерпретатора условием не выдвигается: там, где скилл нужнее всего, ставить
что-либо обычно нельзя.

Проверить, что скрипты не разъехались с заявленной минимальной версией:

```bash
python3 tools/check_compat.py
```

## Как вызывается

Скилл **самозапускающийся**: включается сам, когда в сообщении есть признак инцидента —
«упало на stage», «504 на проде», «почему падает», вставленный стектрейс, ссылка на
Kibana. Явная команда `/incident-detective` тоже работает, но не нужна.

Первым делом скилл заводит план через `todo_write` и дальше строго ему следует, чтобы
не утонуть в логах, забыв спросить базу знаний.

## Про логи

MCP-сервер скилл с собой не тащит. Он ищет уже подключённые в окружении источники
(Kibana, Loki, Grafana, Sentry, k8s — по ключевым словам в списке инструментов и
`settings.json`), а если ничего нет — честно просит у пользователя файл, архив или
ссылку. Никаких выводов «по догадке» без данных.

Парсинг полностью локальный и рассчитан на **неструктурированные и разнородные** логи:
формат определяется построчно (JSON, logfmt, syslog, nginx/apache, стектрейсы Java /
Python / Go / JS, произвольный текст), многострочные записи склеиваются, похожие
сообщения схлопываются в шаблоны с частотами. На выходе — сводка на страницу вместо
десятков тысяч строк.

## Скрипты отдельно от агента

Всё работает и руками, без Qwen:

```bash
S=~/.qwen/skills/incident-detective/scripts

python3 $S/triage.py app.log --repo . --stand stage    # вся цепочка одной командой

python3 $S/parse_logs.py app.log --level ERROR
python3 $S/parse_logs.py app.log --format json > /tmp/parsed.json
python3 $S/parse_logs.py app.log --trace 7f3a9c21      # цепочка одного запроса
python3 $S/parse_logs.py app.log --context 3           # сырые записи группы №3

python3 $S/kb_search.py "оплата висит 504"
python3 $S/kb_search.py --from-parsed /tmp/parsed.json --stand stage

python3 $S/code_hints.py --from-parsed /tmp/parsed.json --repo .
python3 $S/timeline.py --parsed api=/tmp/parsed.json --repo . \
        --event "2026-07-28 12:20|деплой 1.24"

python3 $S/trace.py --log gateway=gw.log --log payment=pay.log --top
python3 $S/trace.py --log gateway=gw.log --log payment=pay.log --id 7f3a-9c
python3 $S/trace.py --log gateway=gw.log --log payment=pay.log --check-clocks

python3 $S/confidence.py --parsed /tmp/parsed.json --kb /tmp/kb.json \
        --code /tmp/code.json --stand stage --service payment-api

python3 $S/kb_add.py --title "..." --stand stage --root-cause "..." \
        --from-parsed /tmp/parsed.json --file src/db/pool.py
```

## База знаний

Источник правды — markdown-файлы: читаются человеком, правятся руками, кладутся в git.
`index.json` производный, пересобирается через `kb_index.py`.

### Где она лежит

Расположение — осознанный выбор, а не умолчание: при **первой записи** скилл спрашивает,
где базу держать, и предлагает варианты — в корне проекта (`memory/knowledgebase/`), в
директории скилла (`kb/`) или свой путь. Вопрос задаётся в момент записи, а не в начале
разбора: во время инцидента диалога о хранении не будет. Директория создаётся только
после ответа — молча база не заводится нигде.

Путь разрешается по порядку: флаг `--kb` → `INCIDENT_KB_DIR` → `memory/knowledgebase/` в
корне текущего репозитория, если она там уже есть, → `kb/` внутри скилла. Переменная
стоит выше базы проекта: это способ намеренно работать с одной базой из разных
репозиториев. Проект перебивает только умолчание — благодаря этому `export`, закреплённый
для одного проекта, не уводит туда записи другого.

Выбор закрепляется строкой в профиле оболочки:

```bash
export INCIDENT_KB_DIR=/path/to/team/incidents
```

Для базы в корне проекта строка не обязательна — там выбор читается по наличию
директории; она нужна, чтобы работать с той же базой из других директорий.

**База в репозитории проекта** едет с ним к команде — и записи попадают в git, откуда из
истории не вычищаются. Записи содержат фрагменты логов; решение принимает тот, кто знает
политики проекта.

**База вне скилла переустановкой не затрагивается.** Спасение записей во временную папку
при перезаписи (см. `install.sh`) касается только базы внутри директории скилла — для
вынесенной наружу оно не требуется и не выполняется.

## Проверки

```bash
python3 tests/run.py            # весь набор
python3 tests/run.py test_parse # один файл проверок
python3 tests/run.py -v         # подробный вывод
```

Ставить ничего не надо: прогон работает на стандартной библиотеке, как и сам скилл.
Запускается из любой директории. Проверка совместимости с Python 3.8
(`tools/check_compat.py`) входит в тот же прогон — точка входа одна. То же самое
выполняется в CI на каждый push и pull request, матрицей `3.8` (минимальная заявленная
версия) и `3.12` (современная — на ней запускает большинство пользователей).

**Что проверяется.** Разбор фикстур с заранее известным ответом: сигнатуры, время
первого события, точка обрыва цепочки. Отсутствие ложных срабатываний — на логе
штатной работы инцидент не находится. Честное «не знаю» — когда контуры не сошлись,
уверенность не поднимается выше гипотезы. Устойчивость ко входу: пустой файл, битая
кодировка, строка чрезмерной длины. Сравнение идёт по JSON-выводу, а не по
markdown: тест не должен падать от переставленного слова в заголовке.

**Что не проверяется.** Поведение модели: самозапуск скилла, порядок шагов разбора,
формулировки вывода. Это инструкции в `SKILL.md`, и проверяются они чтением
спецификации и разбором на живом инциденте, а не запуском скриптов. Скорость —
отдельно, через `tools/bench.py`.

**Как меняется ожидаемый результат.** Только вместе с изменением, которое меняет
поведение, и с объяснением, почему новый ответ верен. Если проверка упала при правке,
не предполагавшей смены поведения, — это регрессия, а не устаревший эталон;
переписывать эталон под текущий вывод скрипта нельзя. Режима массовой перезаписи
эталонов нет намеренно: с ним падение теста превращается в однокнопочную
формальность. Обнаружили, что зафиксированный ответ противоречит спецификации, —
это находка: разбирается отдельно, эталон приводится к тому, каким ответ должен
быть по спеке.

Новая фикстура добавляется вместе с файлом в `tests/expected/`: там сказано, что
именно она проверяет и какой ответ считается верным. Фикстуры синтетические — ни
персональных данных, ни секретов, ни внутренних адресов. Набор лежит в публичном
репозитории и заодно служит примером того, что скилл разрешает сохранять.

## Воспроизводимость и отладка

Две переменные окружения, обе по умолчанию не заданы; без них поведение прежнее.

```bash
export INCIDENT_NOW="2026-07-28 12:00:00"   # «сейчас» для скриптов
```

Задаёт текущее время: год для syslog-записей без года, отсчёт `--since 1h` и `--since
12:30`, дату новой записи базы знаний. Нужна, чтобы чужой разбор воспроизводился на
своей машине и чтобы прогон, прошедший сегодня, не упал в следующем году. Значение,
которое не разбирается как время, — ошибка с сообщением, а не тихий откат на
системные часы.

```bash
export INCIDENT_TRACE_FILE=/tmp/triage-calls.log   # телеметрия вызовов
```

Каждый запущенный скрипт дописывает строку: время, имя, **имена** переданных флагов и
код возврата. Значения аргументов не пишутся — на вход идут фрагменты логов и слова
пользователя, и файл отладки не должен стать ещё одним местом, где они оседают.
В стандартный вывод при этом ничего не добавляется, а недоступный для записи файл
разбор не прерывает.

Смотреть по нему стоит одно: **какие контуры агент реально прогнал**.

```
2026-07-28 12:00:03	parse_logs.py	--format --level	rc=0
2026-07-28 12:00:05	kb_search.py	--from-parsed --format	rc=0
```

Здесь видно, что база знаний спрошена, а `code_hints.py` не запускался — контур кода
пропущен. По тексту ответа агента это не видно: ответ выглядит нормально.

## Спецификация

Проект ведётся по [OpenSpec](https://github.com/Fission-AI/OpenSpec): спецификация —
источник истины, код должен ей соответствовать.

```bash
npx @fission-ai/openspec list --specs        # список capability
npx @fission-ai/openspec show log-parsing    # требования одной capability
npx @fission-ai/openspec validate --specs --strict
```

Capability в `openspec/specs/`:

| Capability | О чём |
|---|---|
| `incident-detection` | самозапуск по признакам инцидента, план через `todo_write`, карточка |
| `log-ingestion` | поиск подключённых источников логов, запрос данных у пользователя |
| `log-parsing` | разбор неструктурированных логов, шаблонизация, сигнатуры |
| `incident-timeline` | сведение источников в одну хронологию |
| `correlation-tracing` | цепочка запроса по correlation id, точка обрыва, часы стендов |
| `confidence-scoring` | уверенность вывода по сошедшимся контурам |
| `knowledge-base` | формат записей, поиск по тексту и сигнатурам, пополнение |

| `performance-budgets` | бюджеты скорости: вызовы инструментов, время скриптов, объём сводки |

Новое изменение предлагается через `/opsx:propose` — команда установлена и для Qwen Code
(`.qwen/commands/`), и для Claude Code (`.claude/commands/`).

## Границы

Скилл только диагностирует: ничего не рестартует, не деплоит и не правит конфиги на
стендах. Правки в код предлагает, но не применяет молча; тикет во внешнем трекере не
заводит без подтверждения — сначала показывает текст. В базу знаний и в тикеты пишет
шаблоны и сигнатуры, а не сырые дампы; очевидные токены и пароли вычищаются при записи.
