# Сквозной разбор: от сообщения до записи в базу

Один инцидент от начала до конца — тем же путём, что проходит агент, но командами,
которые можно выполнить руками. Все данные — из `tests/fixtures/`: логи, запись базы
знаний и маленький git-репозиторий, который строит скрипт ниже. Вывод в этом документе
получен настоящим запуском, поэтому у себя ты получишь то же самое (пути в `--repo` и
`--out` совпадут, если выполнять команды как показано).

Команды выполняются из корня репозитория. `$SKILL_DIR` здесь — `incident-detective/scripts`
(в установленном скилле — путь, по которому его поставили; см. раздел «Скрипты отдельно от
агента» в `README.md`).

## Сообщение пользователя

> В логах payment-api на stage вылетает таймаут, оплаты не проходят. Вот файл:
> `tests/fixtures/logs/payment.log`. Разберись, пожалуйста.

## План работ

Первым шагом агент заводит план (шаг 0 `SKILL.md`) и дальше строго следует ему — здесь
он для ориентира, командой это не выполняется:

```
1. Предпроверка окружения и первый взгляд на базу знаний
2. Собрать карточку инцидента; спросить карту источников по стенду и сервису
3. Обследовать каналы и выгрузить логи окном вокруг инцидента
4. Разбор одной командой: логи, база по сигнатурам, код, уверенность
5. Прочитать найденные места в коде и объяснить механику падения
6. Сформулировать вывод с доказательствами
7. Пополнить базу знаний по итогам разбора
8. Предложить следующий шаг: правки, баг или задача
```

Пункты 3–6 из этого плана в разборе ниже покрывает один запуск `triage.py` (шаг 4 плана
объединяет базу, код и уверенность одним запуском — они не зависят друг от друга).

## Подготовка: демо-репозиторий для контура кода

Логи и запись базы знаний уже в репозитории (`tests/fixtures/logs/payment.log`,
`tests/fixtures/kb/INC-2026-07-001-payment-pool-exhausted.md`). Контуру кода дополнительно
нужен git-репозиторий с файлом, к которому относится ошибка — им не может быть сам
`hakaton-skill` (это репозиторий скилла, а не сервиса `payment-api`), поэтому маленький
демо-репозиторий собирается отдельно:

```bash
python3 tests/make_demo_repo.py /tmp/incident-demo-repo
```

Скрипт идемпотентен и создаёт один файл (`src/payment/pool.py` с классом
`ConnectionTimeoutError`, тем же, что в логе) и один коммит с фиксированной датой. Ни
сети, ни платформы для этого не нужно — только `python3` и `git`, оба уже входят в
требования к окружению.

## Запуск разбора

```bash
INCIDENT_NOW="2026-07-28 16:30:00" python3 incident-detective/scripts/triage.py \
    tests/fixtures/logs/payment.log \
    --repo /tmp/incident-demo-repo \
    --kb tests/fixtures/kb \
    --stand stage --service payment-api \
    --out /tmp/incident-demo-out
```

Вывод (сокращён до сути каждого раздела — раскрыт целиком после):

```
# Разбор инцидента

- Пройдено контуров: Логи, База знаний, Код, Уверенность
```

## Сводка логов

Из вывода `triage.py` (тот же результат даёт `parse_logs.py tests/fixtures/logs/payment.log`):

```
- Источники: payment.log (4)
- Записей: 4
- Период: 2026-07-28 16:20:02 — 2026-07-28 16:21:12 (1 мин)
- Уровни: INFO=3 ERROR=1

### Ошибки и предупреждения (топ 1 из 1 шаблонов)

**#1 · 1× · ERROR**
`ConnectionTimeoutError: timed out waiting for connection from pool after <n> ms`
  first 2026-07-28 16:20:03 · компонент: payment-api · файл: payment.log

### Сигнатуры для базы знаний

- `ConnectionTimeoutError` (1×)
- `tmpl:ConnectionTimeoutError: timed out waiting for connection from pool after <n> ms` (1×)
```

Один шаблон ошибки на четыре записи — сразу видно, из-за чего разбор, без чтения сырого
лога целиком.

## Совпадение в базе знаний

```
## База знаний: найдено 1 из 3

### INC-2026-07-001 — payment-api отдаёт таймауты: исчерпан пул соединений к базе
- 2026-07-14 · status resolved · severity high · stands: stage · services: payment-api
- релевантность: 51.8 — сигнатура 100%: tmpl:ConnectionTimeoutError...; сигнатура 100%: ConnectionTimeoutError
- **Причина:** Размер пула соединений (20) меньше числа параллельных обработчиков после
  включения батчевой обработки платежей.
- **Решение:** Подняли размер пула до 60 и вернули таймаут ожидания к 2 с.
```

Похожий инцидент уже разбирали две недели назад — сигнатура совпала на 100%. Это повод
проверить ту же причину, а не готовый ответ: «совпадение сигнатуры не доказывает ту же
причину», как и написано в самом выводе.

## Контур кода

```
## Связь ошибок с кодом

### Где порождается текст ошибки

- `src/payment/pool.py:4` — class ConnectionTimeoutError(Exception):
- `src/payment/pool.py:11` — raise ConnectionTimeoutError(

### Коммиты в окне инцидента (сутки до первой ошибки)

- `5214f89` 2026-07-27 20:00 · incident-detective-demo · add connection pool
```

Стектрейса в логе нет — контур ищет по литеральному тексту сообщения и находит место, где
класс исключения объявлен и где выбрасывается. Коммит в окне инцидента есть, но, как честно
сказано дальше в выводе («Что настораживает»), он не трогает найденные файлы — совпадение по
времени само по себе не доказательство.

## Уровень уверенности

```
## Уверенность в выводе: 0.39 — гипотеза

| Контур | Вес | Оценка | Вклад |
|---|---|---|---|
| Логи | 0.30 | 0.55 | 0.17 |
| Код | 0.30 | 0.25 | 0.07 |
| База знаний | 0.25 | 0.60 | 0.15 |
| Цепочка запроса | 0.15 | — | 0.00 |
```

Три контура из четырёх дали хоть что-то, но ни один — уверенно: ошибка единичная, коммит в
окне не подтверждён, а исход прошлой записи в базе не проверен. Отсюда — «гипотеза», а не
«вероятная причина»: подтверждено данными разбор здесь быть не может, и вывод обязан это
показать прямо, а не звучать увереннее, чем есть основания.

## Вывод

По логам и совпадению с `INC-2026-07-001`: вероятная причина — пул соединений к платёжному
провайдеру рассчитан на меньшую параллельность, чем даёт текущая нагрузка на stage.
Подтверждено это не может быть без данных, которых в разборе не хватает: числа активных
соединений на момент инцидента и подтверждения, что коммит `5214f89` действительно правил
пул, а не что-то соседнее. Ответ агента в таком разборе так и звучит — с явным «предполагаю»,
а не как установленный факт.

## Предложение следующего шага

Уровень «гипотеза» по таблице из `references/next-step.md` ведёт к варианту **задача на
доисследование** (не «баг» — причина ещё не проверена, значит и тикет с ней будет с
выдуманным основанием) и не к правкам в код: подтверждения слишком мало. Агент задаёт этот
выбор инструментом вопроса с вариантами, не решая за пользователя.

## Запись в базу знаний

```bash
python3 incident-detective/scripts/kb_add.py \
    --title "payment-api: ConnectionTimeoutError, требует проверки против INC-2026-07-001" \
    --stand stage --service payment-api \
    --root-cause "гипотеза: пул соединений меньше параллельности нагрузки, см. INC-2026-07-001" \
    --from-parsed /tmp/incident-demo-out/parsed.json \
    --file src/payment/pool.py --related INC-2026-07-001 \
    --outcome unverified --kb /tmp/incident-demo-out/kb --dry-run
```

`--dry-run` показывает запись, но не пишет её — в этом документе так и остаётся, чтобы
повторный запуск не плодил файлы. Без флага запись легла бы в указанную `--kb`-директорию:

```
---
id: INC-2026-07-001
title: "payment-api: ConnectionTimeoutError, требует проверки против INC-2026-07-001"
...
outcome: unverified
outcome_date: 2026-07-28
files: [src/payment/pool.py]
related: [INC-2026-07-001]
signatures:
  - "ConnectionTimeoutError"
  - "tmpl:ConnectionTimeoutError: timed out waiting for connection from pool after <n> ms"
---
```

`outcome: unverified` — честно, пока причина не подтверждена: запись помогает следующему
разбору выйти на это место сразу, но не выдаёт гипотезу за проверенный ответ. Когда причина
подтвердится или будет отброшена, запись дополняется тем же `kb_add.py --update` с
`--outcome confirmed` или `--outcome refuted`.


## Второй разбор на том же стенде

Через неделю на `stage` снова таймауты в `payment-api`. Разница с первым разом — в самом
начале: искать источник логов заново не нужно.

Карта пополняется в первом же разборе, сразу после успешной выгрузки и до парсинга — пока
запрос и адрес под рукой:

```bash
python3 incident-detective/scripts/kb_add.py --kind source \
    --stand stage --service payment-api \
    --source kind=mcp,server=kibana-mcp,tool=search_logs \
    --address 'index=logs-stage-*' \
    --query 'env:stage AND service:payment-api AND level:(ERROR OR FATAL)' \
    --fields time=@timestamp,level=log.level,message=message \
    --kb /tmp/incident-demo-out/kb --dry-run
```

Второй разбор начинается с вопроса к карте (здесь — по готовой фикстуре
`tests/fixtures/kb_sources`, где такая запись уже лежит):

```bash
python3 incident-detective/scripts/kb_search.py --sources \
    --stand stage --service payment-api --kb tests/fixtures/kb_sources
```

```
# Карта источников: 1 из 2

Запрос: стенд: stage · сервис: payment-api

## SRC-stage-payment-api
- стенд: stage · сервисы: payment-api
- источник: kind=mcp, server=kibana-mcp, tool=search_logs
- адрес: index=logs-stage-*
- запрос: `env:stage AND service:payment-api AND level:(ERROR OR FATAL)`
- соответствие полей: time=@timestamp, level=log.level, message=message
- подтверждён: 2026-07-20 (возраст 9 дн.)
- отвергнут: loki-mcp — пуст для этой пары (2026-07-20, 9 дн. назад): стенд не пишет в loki
```

Источник, инструмент, индекс и рабочий запрос известны — перебор каналов не запускается, а
вопрос «откуда брать логи» пользователю не задаётся. Отвергнутый `loki-mcp` в перебор не
попадает, и причина названа прямо в выдаче: решение видимое, а не молчаливое.

Осмотр состава агент всё равно делает — он стоит близко к нулю и нужен, чтобы заметить
инструмент, подключённый между разборами. По карте идёт **обращение**, а не осмотр. Если
источник за неделю отвалился, кандидаты уже собраны тем же осмотром: разбор переходит к
ним, не повторяя круг, а запись карты помечается как неподтвердившаяся, но не удаляется
молча.

Источник, который проверили и признали бесполезным, помечается так:

```bash
python3 incident-detective/scripts/kb_add.py --mark-checked 'loki-mcp' \
    --verdict empty --note 'стенд не пишет в loki' \
    --stand stage --service payment-api \
    --kb /tmp/incident-demo-out/kb --dry-run
```

Дальше разбор идёт как обычно, с шага выгрузки. Сэкономлен самый дорогой участок — перебор
источников до первой строки данных.

## Регрессия на другом стенде

Та же сигнатура на других стендах ищется одной командой, а не перебором фильтров:

```bash
python3 incident-detective/scripts/kb_search.py --signature ConnectionTimeoutError \
    --exclude-stand prod --kb tests/fixtures/kb_sources
```

```
# База знаний: найдено 1 из 2

## INC-2026-06-010 — payment-api на stage: таймауты из-за исчерпанного пула соединений
- 2026-06-10 · status resolved · severity high · stands: stage · services: payment-api
- исход: не проверена
- релевантность: 16.1 — сигнатура 100%: ConnectionTimeoutError
```

Выдача называет стенд, дату и исход каждого совпадения — видно, что на `stage` это уже
случалось и чем закончилось. Записи карты в такую выдачу не попадают: виды записей не
смешиваются. Если совпадений нет, это формулируется как «на других стендах не
встречалась» — отличимо от «записей в базе нет вообще».
