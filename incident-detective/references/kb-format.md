# Формат базы знаний

База — обычные markdown-файлы в `kb/`, по файлу на инцидент, плюс сгенерированный `kb/index.json`. Источник правды — markdown: он читается человеком, правится руками и кладётся в git. Индекс всегда можно пересобрать: `python3 scripts/kb_index.py`.

## Где лежит база

Путь разрешается по порядку, первый сработавший шаг выигрывает:

| # | Шаг | Когда срабатывает |
|---|---|---|
| 1 | флаг `--kb <путь>` | задан в запуске скрипта |
| 2 | env `INCIDENT_KB_DIR` | задана в окружении |
| 3 | `memory/knowledgebase/` в корне текущего репозитория | директория **уже существует** |
| 4 | `kb/` внутри директории скилла | во всех остальных случаях |

Третий шаг — не поиск базы по кандидатам, а чтение обратно уже сделанного выбора: эта директория появляется только после явного ответа пользователя на вопрос о расположении. Скилл её не создаёт при разрешении пути и не заводит молча. Вне git-репозитория шаг пропускается.

Порядок важен: `INCIDENT_KB_DIR` стоит **выше** базы репозитория. Это способ намеренно работать с одной базой из разных проектов, и он остаётся сильнее. Проект перебивает только умолчание — иначе `export`, закреплённый для проекта A, молча уводил бы туда записи проекта B.

Расположение не задано ни одним из шагов, а база внутри скилла пуста — `kb_add.py` не пишет ничего: он завершается кодом 3 и сообщением «расположение базы знаний не выбрано». Вопрос задаёт агент — при первой записи, не в начале разбора, — и повторяет запуск с `--kb`.

Выбор закрепляется строкой в профиле оболочки:

```bash
export INCIDENT_KB_DIR=/path/to/team/incidents
```

Для базы в корне проекта строка не обязательна: в этом репозитории выбор читается по наличию директории. Она нужна, чтобы работать с той же базой из других директорий.

База в репозитории проекта означает, что записи попадут в git и из истории не вычищаются. Записи содержат фрагменты логов — решение принимает тот, кто знает политики проекта.

## Имя файла

`INC-<YYYY>-<MM>-<NNN>-<короткий-слаг>.md`, например `INC-2026-07-001-payment-504-pool.md`. Номер `kb_add.py` выдаёт сам.

Заполненный пример записи целиком — [../templates/kb-entry-example.md](../templates/kb-entry-example.md). В самой базе он не лежит: пустая база на свежей установке — это признак того, что расположение ещё не выбрано, и демо-запись его бы сломала.

## Структура записи

```markdown
---
id: INC-2026-07-001
title: 504 на оплате из-за исчерпания пула соединений
date: 2026-07-28
stands: [stage, prod]
services: [payment-api, postgres]
tags: [timeout, db, pool, 504]
severity: high
status: resolved
outcome: unverified
signatures:
  - "java.sql.SQLTimeoutException"
  - "http_status=504"
  - "tmpl:connection pool exhausted, waited <n> ms"
---

## Симптомы
Что видел пользователь и что было в мониторинге. Формулировки, по которым
этот инцидент будут искать в следующий раз — включая «народные» («оплата висит»).

## Диагностика
Как дошли до причины: какие логи смотрели, какие запросы делали, что отсекли.
Самая ценная часть — она экономит время в следующий раз.

## Причина
Одна-две фразы по существу, без пересказа расследования.

## Решение
Что сделали. Если был воркэраунд и отдельно постоянный фикс — оба, помечены.

## Проверка
Как убедиться, что починилось.

## Отличительные признаки
Необязательно. Чем текущий случай отличается от похожего, несмотря на совпадение
сигнатуры.

## Заметки
Ссылки на тикеты, PR, дашборды. Грабли, на которые не надо наступать снова.
```

## Поля frontmatter

| Поле | Обяз. | Смысл |
|---|---|---|
| `id` | да | `INC-YYYY-MM-NNN`, уникален |
| `title` | да | одна строка, суть + причина, а не только симптом |
| `date` | да | дата разбора, `YYYY-MM-DD` |
| `stands` | да | стенды, где встречался: `dev`, `test`, `stage`, `prod`, имена контуров |
| `services` | нет | затронутые сервисы/компоненты |
| `tags` | да | ключевые слова для поиска, нижний регистр |
| `severity` | нет | `low` / `medium` / `high` / `critical` |
| `status` | нет | `resolved` / `workaround` / `open` / `wontfix` |
| `outcome` | нет | `confirmed` / `refuted` / `unverified` — достоверность разбора, не путать со `status` |
| `outcome_date` | нет | дата, когда исход стал известен, `YYYY-MM-DD` |
| `reuse_count` | нет | сколько раз запись пригодилась при повторе инцидента |
| `reused_at` | нет | дата последнего переиспользования |
| `signatures` | нет | сигнатуры из `parse_logs.py` — главный канал точного поиска |
| `related` | нет | id связанных инцидентов |

## `status` и `outcome` — разные вещи

`status` описывает **инцидент**: чинили, починили, наблюдаем — `resolved`, `workaround`,
`open`, `wontfix`. `outcome` описывает **достоверность разбора**: подтвердилась ли
названная причина на практике. Инцидент бывает закрыт (`status: resolved`) с причиной,
которая на самом деле не подтвердилась (`outcome: refuted`) — это ровно тот случай, ради
которого поле введено, и `outcome` из `status` не выводится.

Значения `outcome`:

- `confirmed` — причина проверена на практике, фикс сработал;
- `refuted` — причина не подтвердилась; запись не удаляется, но и не выдаётся наравне с
  подтверждёнными — она рассказывает, какая гипотеза не сработала;
- `unverified` (или поле отсутствует) — фикс ещё не проверен практикой; это значение по
  умолчанию для новой записи.

## Отличительные признаки

Короткие проверяемые наблюдения — по чему видно, что текущий случай **не** тот, что
описан в записи, несмотря на совпадение сигнатуры. Показываются в выдаче поиска рядом с
совпадением, до того как разбор пойдёт по версии записи.

Годный признак называет конкретное наблюдение, которое можно проверить сразу:

- «если в логе есть строка о блокировке таблицы (`lock wait timeout`) — это другой
  инцидент, не пул соединений»;
- «если ошибка идёт с одного хоста, а не со всех реплик — дело не в конфиге пула»;
- «если `pool.max_size` в конфиге уже ≥ 60 — фикс из этой записи неприменим».

Негодный признак сводится к общему указанию провести исследование, а не к наблюдению —
такой не работает как проверка на месте, за секунды:

- «убедитесь, что причина та же» — не называет, что именно смотреть;
- «сверьте условия» — неясно, какие условия и по какому значению;
- «проверьте, не другая ли это проблема» — не даёт критерия проверки.

Поле необязательное: если отличительного признака нет, раздел просто не заполняется —
формальная отписка хуже отсутствия признака.

## Про сигнатуры

Сигнатуры — то, чем запись цепляется за будущие логи. Три вида:

- `java.sql.SQLTimeoutException` — класс исключения или код ошибки;
- `http_status=504` — статус/код;
- `tmpl:connection pool exhausted, waited <n> ms` — шаблон сообщения с замаскированными переменными частями.

Берутся из `--from-parsed` автоматически, руками добавлять обычно не нужно. Важно: сигнатура — это то, что стабильно между инцидентами. Конкретные id, хосты и числа туда не попадают — и не должны.

## Маскирование

Запись в базу знаний (`kb_add.py`), текст тикета и постмортем проходят очистку общей
функцией (`kb_common.scrub_text` для скриптов, то же правило по инструкции — для
тикета и постмортема). Значение заменяется меткой вида, а не стирается: запись
остаётся читаемой и пригодной для поиска.

| Вид данных | Как распознаётся | Метка |
|---|---|---|
| email | форма адреса | `<email>` |
| телефон | распространённые форматы записи | `<phone>` |
| номер платёжной карты | 13–19 цифр, проходит контрольную сумму Луна | `<card:…1111>` — последние четыре цифры сохраняются |
| номер счёта | 20-значный номер | `<account>` |
| идентификатор физлица | СНИЛС, серия и номер паспорта | `<person_id>` |
| секрет по имени поля | `password=...`, `token: ...`, `Authorization: Bearer ...` | `<поле>=<redacted>` |
| токен по форме значения | JWT, распознаваемые префиксы ключей API | `<token>` |
| учётные данные в URL | `scheme://user:pass@host` | `scheme://<redacted>@host` |

Шестнадцатизначное число, не прошедшее контрольную сумму Луна, картой не считается и
остаётся в записи нетронутым — иначе идентификаторы и счётчики той же длины терялись бы
без причины.

Одинаковое значение в пределах одной записи маскируется одинаково — метка зависит только
от вида данных. Сопоставление метки с исходным значением никуда не сохраняется и
восстановить исходное значение по нему нельзя.

**Что не маскируется — сознательно, не по недосмотру:** идентификаторы запросов и trace
id, номера заказов и транзакций, имена сервисов и хостов, версии, пути в коде,
IP-адреса. Без них разбор не воспроизвести, а персональными данными они не являются.

Что-то было замаскировано при записи — `kb_add.py` печатает сводку по видам без
исходных значений, а `--dry-run` показывает уже очищенный текст вместе с той же
сводкой. Лишнее срабатывание (замаскирован нужный идентификатор) видно из сводки до
сохранения — можно поправить текст и повторить запись.

## Правила заполнения

- **Пиши после разбора, а не в процессе** — иначе в записи останутся тупиковые версии.
- **Без секретов.** Токены, пароли, ключи, персональные данные — не переносить из логов. Сырые дампы не класть, только шаблоны. Очистка — последний рубеж, а не разрешение вставлять логи целиком.
- **Симптомы — словами пользователя.** Искать будут именно так, а не по имени exception.
- **Дубли не плодить.** Повторился инцидент — дополни существующую запись: добавь стенд, дату, новую сигнатуру, уточнение причины. `kb_search.py` перед созданием записи прогоняй всегда.
- **Незакрытые инциденты тоже полезны.** `status: open` с описанием, что уже проверено и отсечено, экономит время не меньше решённых.

## Поиск

```bash
# по словам
python3 scripts/kb_search.py "оплата висит 504 stage"

# по результату разбора логов (точнее всего)
python3 scripts/kb_search.py --from-parsed /tmp/parsed.json --stand stage

# фильтры
python3 scripts/kb_search.py "таймаут" --stand prod --service payment-api --tag db --top 5
python3 scripts/kb_search.py --list          # все записи
python3 scripts/kb_search.py "..." --format json
```

Скоринг: совпадение сигнатуры весит больше всего, дальше — теги и заголовок, потом симптомы, потом тело. Учитывается русская и английская морфология (сравнение по префиксам основ), так что «таймауты» найдут «таймаут».
