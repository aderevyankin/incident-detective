# Предпроверка окружения и ограниченный режим

Скилл держится на скриптах: `parse_logs.py` даёт сигнатуры, на которых работают все три
контура, `confidence.py` определяет, каким языком формулируется вывод. Если подходящего
`python3` в системе нет, это надо выяснить в начале разбора, а не посреди него — и сказать
пользователю прямо.

Файл описывает: команду предпроверки, что говорить в каждом исходе, как разбирать инцидент
без скриптов и чего в таком разборе делать нельзя. Место в разборе — шаг 1 `SKILL.md`, сразу
после плана и до любого скрипта.

## 1. Команда предпроверки

Одна команда, до первого скрипта, один раз за разбор:

```bash
python3 -c "import sys; v = sys.version.split()[0]; ok = sys.version_info >= (3, 8); print('python3: ' + v + (' — пригоден' if ok else ' — ниже 3.8, скрипты скилла не запустятся'))" 2>/dev/null || echo "python3: не найден"; command -v git >/dev/null 2>&1 && echo "git: есть" || echo "git: нет — контур кода будет без git-истории"
```

Проверка не может опираться на скрипт скилла: она как раз и выясняет, запускаются ли
скрипты. Поэтому это команда оболочки, а не `preflight.py`.

Результат известен на весь разбор — перед каждым следующим скриптом её не повторяй.

## 2. Что говорить пользователю

Результат объявляется в чат **до** начала работы контуров. Называй найденное, а не только
вердикт: «не могу» без подробностей пользователю ничего не даёт.

| Исход | Что сказать |
|---|---|
| `python3: 3.11.4 — пригоден` | «Окружение проверил: python3 3.11.4, git есть — разбор в полном режиме.» Одна строка, дальше по плану |
| `python3: не найден` | «python3 в системе нет. Скрипты разбора недоступны, продолжаю в ограниченном режиме: базу знаний прочитаю как есть, логи разберу выборочно. Сводку по шаблонам и частотам, хронологию и подсчёт уверенности собрать не смогу.» |
| `python3: 3.6.9 — ниже 3.8` | То же, но с обеими версиями: «Найден python3 3.6.9, скриптам нужен 3.8 или новее.» |
| `git: нет` | «git недоступен — контур кода отработает по файлам, но без истории коммитов.» Остальное в полном режиме |

Три правила формулировки:

- **Установка не выдвигается условием.** Скилл часто работает в закрытом контуре, где
  поставить интерпретатор нельзя, и требование «сначала установите python3» там означает
  «разбора не будет». Упомянуть недостающее один раз как факт — достаточно.
- **Ограничение называется до разбора, а не после.** Пользователь должен решить, стоит ли
  вообще выгружать логи, зная, чем закончится.
- **Никакого «попробую обойти».** Режим объявлен — дальше работаем по нему.

## 3. Разбор без скриптов

Структура из трёх контуров сохраняется, меняются инструменты.

**База знаний.** Записи лежат в `kb/` обычным markdown именно ради этого случая: читай
`kb/index.json` для обзора, `kb/INC-*.md` — целиком, поиск по тексту — `grep -ril` по
директории базы. Контур работает почти в полную силу, начинать по-прежнему с него.

**Логи.** Только точечные выборки средствами оболочки: `grep` по классам исключений и
HTTP-статусам, `tail`/`sed` по окну времени, `sort | uniq -c | sort -rn` для грубой частоты.
Чего не будет: определения формата построчно, склейки многострочных записей и стектрейсов,
шаблонизации сообщений, сигнатур, гистограммы, окна инцидента. Это не «то же самое руками» —
это заметно меньше, и в ответе так и надо сказать.

**Код.** Файлы читаются и ищутся как обычно, стектрейс разбирается глазами. Без `git` не
будет коммитов в окне инцидента; с `git`, но без скриптов, историю можно посмотреть
напрямую (`git log --since=... --until=...`).

**Хронология и цепочка запроса.** Не собираются. Если сервисов несколько, скажи, что
определить точку обрыва по correlation id нечем, и не выдавай порядок сообщений в файле за
последовательность событий.

**Пополнение базы знаний.** Остаётся возможным: запись создаётся вручную по формату из
[kb-format.md](kb-format.md), имя — следующий свободный `INC-<год>-<месяц>-<номер>`. Секреты
вычищаются так же, как это делает `kb_add.py`. В ответе отметь, что `index.json` не
пересобран — его приведёт в порядок `kb_index.py`, когда появится интерпретатор.

## 4. Уровень уверенности: потолок «гипотеза»

Без `confidence.py` уровень вывода **не поднимается выше «гипотезы»**, и причина этого
называется в ответе.

Это не перестраховка. Вес контура в оценке стоит на том, чего ручное чтение не даёт:
устойчивой сигнатуре, окне, частоте, первой ошибке в цепочке. Прочитанный глазами лог —
наблюдение, а не пройденный контур. Даже точное совпадение с записью базы знаний уровень не
поднимает: одна опора причину не доказывает — это верно и в полном режиме.

Формулировка в выводе: «Причина — гипотеза: скрипты разбора были недоступны, контуры логов и
кода не проверялись полноценно».

## 5. Чего делать нельзя

- **Подбирать другой интерпретатор.** Ни `python`, ни `python2`, ни найденный в системе
  бинарник иной версии. Скрипты рассчитаны на 3.8+, а «вроде запустилось» на неподходящей
  версии даёт тихо неверный разбор вместо честного отказа.
- **Писать свой парсер на ходу.** Ни на Python, ни на другом языке, ни во временный файл.
  Одноразовый парсер, написанный по ходу разбора, никем не проверен, а выглядит как
  результат работы скилла.
- **Выдавать ручное чтение за работу контура.** Прочитанное глазами приводится как
  наблюдение со ссылкой на строки. Контур при этом остаётся непройденным — см. раздел 4.
- **Молчать о режиме.** Ограниченный разбор, поданный как обычный, хуже отсутствия разбора:
  по нему принимают решения с чужим уровнем доверия.

## 6. Когда окружение появилось

Пользователь поставил интерпретатор или перешёл на машину, где он есть, — предпроверку
имеет смысл выполнить заново. Полный разбор скриптами делается с нуля: он даёт сигнатуры и
оценку, которых в ограниченном режиме не было. Потолок «гипотезы» после этого не применяется,
уровень считается обычным порядком.
