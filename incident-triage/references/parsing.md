# Парсинг неструктурированных логов

`scripts/parse_logs.py` — stdlib-only, Python 3.8+. Задача скрипта: превратить произвольную кучу строк в короткую сводку, по которой можно рассуждать, и в набор **сигнатур** для поиска по базе знаний.

## Что он делает

1. **Читает** файлы, glob-маски, директории, `.gz`/`.bz2`/`.xz`/`.zip`, а также stdin (`-`).
2. **Определяет формат каждой строки** независимо — в одном файле спокойно уживаются JSON-строки от одного сервиса и nginx-access от другого:
   - JSON lines (`{"level":"error","ts":...}`) — поля `time/timestamp/@timestamp/ts/date`, `level/severity/lvl`, `message/msg/log/short_message`;
   - logfmt (`level=error msg="..." dur=1.2s`);
   - nginx/apache combined и common;
   - syslog (`Jul 28 12:33:44 host app[123]:`);
   - «человеческий» текст с таймстемпом и уровнем в начале строки;
   - всё остальное — как plain-запись.
3. **Склеивает многострочные записи.** Строка считается началом новой записи, если в её начале есть таймстемп, или это JSON-объект, или она подходит под access-log. Всё прочее — продолжение предыдущей. Так стектрейсы Java/Python/Go, SQL-дампы и XML не рассыпаются на сотни «ошибок».
4. **Нормализует уровень**: `WARN/WARNING/W`, `ERR/ERROR/E`, `FATAL/CRIT/CRITICAL/PANIC/EMERG` и т.д. приводятся к общей шкале. У access-логов уровень выводится из HTTP-статуса (5xx → ERROR, 4xx → WARN).
5. **Шаблонизирует сообщения**: маскирует изменчивые части — числа, UUID, IP, hex-строки, кавычки, пути, URL, email, длинные идентификаторы. `user 8213 not found` и `user 91 not found` схлопываются в один шаблон `user <n> not found` с счётчиком 2.
6. **Считает статистику**: частота шаблонов, first/last seen, гистограмма по минутам, распределение уровней, топ exception-классов, HTTP-статусы.
7. **Извлекает сигнатуры** — компактные строки вида `java.sql.SQLTimeoutException`, `http_status=504`, `tmpl:connection pool exhausted for <str>`. Это то, что переживает смену версий и по чему база знаний ищет похожие случаи.

## Использование

```bash
# базовая сводка
python3 scripts/parse_logs.py app.log

# только ошибки, топ-15 шаблонов
python3 scripts/parse_logs.py 'logs/**/*.log' --level ERROR --top 15

# окно времени
python3 scripts/parse_logs.py app.log --since "2026-07-28 12:00" --until "2026-07-28 13:00"

# из stdin
kubectl logs -n stage payment-api --since=1h | python3 scripts/parse_logs.py -

# машинный вывод для kb_search / kb_add
python3 scripts/parse_logs.py app.log --format json > /tmp/parsed.json

# сырые записи конкретной группы (номер из сводки)
python3 scripts/parse_logs.py app.log --context 3

# всё по одному request/trace id
python3 scripts/parse_logs.py app.log --trace 7f3a9c21
```

Флаги: `--level`, `--since`, `--until`, `--grep`, `--top`, `--context N`, `--trace ID`, `--histogram`, `--format md|json`, `--max-lines`, `--encoding`.

## Как читать сводку

- **Доминирующий шаблон важнее редкого.** Одинокий exception на фоне 4000 однотипных таймаутов — обычно следствие, а не причина.
- **First seen** — точка старта. Сверь с деплоем, релизом, словами пользователя. Если ошибки шли и до инцидента — они, вероятно, фоновый шум и не относятся к делу.
- **Всплеск на гистограмме** локализует момент. Ровный фон весь период — проблема не новая.
- **Первая ошибка в цепочке trace id** ближе к причине, чем последняя. Смотри `--trace`.
- **Пустой результат по ERROR** — не значит «всё хорошо». Перезапусти без `--level`: падение могло логироваться как INFO, или процесс убили снаружи (OOM, SIGKILL) и в логе просто обрыв.

## Ограничения, о которых стоит помнить

- Год в syslog-формате (`Jul 28 12:33:44`) отсутствует — подставляется текущий; на данных с прошлого года время съедет.
- Таймзоны: если в логе её нет, время считается наивным и сравнивается как есть. При сведении логов разных сервисов расхождение в пару часов — почти всегда TZ, а не реальная задержка.
- Шаблонизация агрессивна: очень разные сообщения с одинаковым скелетом могут слиться. Перед выводом всегда проверяй сырые записи через `--context`.
- Бинарный мусор и очень длинные строки обрезаются (по умолчанию 8 КБ на строку).
