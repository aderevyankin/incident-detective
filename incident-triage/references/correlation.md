# Сквозная цепочка запроса между сервисами

Логи одного сервиса отвечают на вопрос «что у меня сломалось». Когда сервисов
несколько, вопрос другой: **чей сбой был первым, а чей — реакцией на него**.
Gateway пишет `504 upstream timed out`, payment-api пишет `SQLTimeoutException`,
и по отдельным логам оба выглядят виноватыми одинаково.

Связывает их **correlation id** — идентификатор запроса, который сервисы
передают друг другу в заголовках и пишут в каждую строку лога.

## Как выглядит id

Скрипты ищут его в полях `trace_id`, `traceId`, `request_id`, `requestId`,
`correlation_id`, `correlationId`, `x-request-id`, `rqUID`, `span_id`, `req_id`
для JSON и logfmt, а в произвольном тексте — по шаблону `trace-id=<значение>`
и его вариантам.

```
{"time":"...","level":"error","trace_id":"7f3a-9c","msg":"upstream timed out"}
time=... level=error request_id=7f3a-9c msg="charge failed"
2026-07-28 12:31:31 ERROR [correlation-id=7f3a-9c] charge failed
```

Нет id ни в одном формате — цепочку собрать не из чего. Тогда остаётся разбор
по времени (`timeline.py`), и это заметно слабее: одновременность не равна
причинности.

## Порядок работы

```bash
# 1. Какие запросы вообще падали
python3 $SKILL_DIR/scripts/trace.py \
  --log gateway=gw.log --log payment=pay.log --log inventory=inv.log --top

# 2. Цепочка конкретного запроса
python3 $SKILL_DIR/scripts/trace.py \
  --log gateway=gw.log --log payment=pay.log --id 7f3a-9c

# 3. Сырые записи цепочки, если нужен текст ошибок
python3 $SKILL_DIR/scripts/trace.py --log ... --id 7f3a-9c --records 20
```

Метка перед `=` — имя сервиса в выводе. Без неё берётся имя файла, и цепочка
читается хуже: `gw.log → pay.log` вместо `gateway → payment`.

## Что читать в выводе

| Колонка | О чём говорит |
|---|---|
| **первая запись** | когда запрос дошёл до сервиса |
| **внутри** | сколько сервис с ним работал |
| **пауза от предыдущего** | сколько ждал вызывающий; здесь видно узкое место |
| **ошибок / статусы** | где именно посыпалось |

Ниже таблицы — **первая ошибка по времени**. Это и есть кандидат в причину.
Вызывающий сервис почти всегда пишет свою ошибку позже: сначала падает
нижний, потом верхний отваливается по таймауту. Читать цепочку сверху вниз и
винить первый сервис в списке — типичная ошибка разбора.

## Часы расходятся

На стендах время сервисов не синхронизировано, и хоп может выглядеть уехавшим
назад: ответ будто раньше запроса. Скрипт помечает такое ⚠ и умеет оценить
расхождение:

```bash
python3 $SKILL_DIR/scripts/trace.py --log gateway=gw.log --log payment=pay.log --check-clocks
```

Оценка строится на разнице первых отметок одного и того же запроса у пары
сервисов. Если по многим запросам разница держится около одного значения —
это похоже на постоянный сдвиг часов: живая задержка так себя не ведёт, она
гуляет от запроса к запросу.

Поправка **не применяется автоматически** — иначе в отчёте появилось бы время,
которого не было в логах. Задаётся руками:

```bash
python3 $SKILL_DIR/scripts/trace.py --log ... --offset payment=-5.2 --id 7f3a-9c
```

Вывод про часы косвенный: стабильная задержка и сдвиг часов выглядят
одинаково. Прежде чем опираться на него, сверься с системным временем стендов.

## Границы метода

- Цепочка показывает **последовательность**, а не причину. «Payment упал
  первым» — наблюдение; почему упал, отвечают контуры логов и кода.
- Id теряется на асинхронных границах: очереди, ретраи и фоновые задачи часто
  идут уже без него. Обрыв цепочки на брокере — не признак поломки брокера.
- Один сервис писал не все записи с id — цепочка будет неполной и создаст
  ложное впечатление, что сервис отработал быстро. Сверяй число записей на хоп.
