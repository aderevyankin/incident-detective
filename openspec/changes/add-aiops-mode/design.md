## Context

Скилл спроектирован под диалог: план работ, уточняющие вопросы вариантами, выбор
расположения базы знаний, предложение следующего шага. В AIOps человека в контуре нет —
обвязка получает алерт и запускает клиент одной командой:

```bash
INCIDENT_MODE=auto INCIDENT_NOW="2026-07-28 12:31:00" INCIDENT_KB_DIR=/srv/incident-kb \
gigacode -p "Разбери инцидент. Логи: /var/log/payment-api/, отчёт положи в /srv/incident-runs/2026-07-28-0031/" \
  --output-format json --channel CI --max-session-turns 20
# на выходе: /srv/incident-runs/2026-07-28-0031/report.json
```

Такой запуск на GigaCode уже проверен и работает — в проверочном прогоне путь к логам был
подставлен реальный, а не заглушкой. Обвязка задаёт **оба** пути явно: откуда читать логи
и куда положить отчёт. Отчёт в неизвестной обвязке временной директории бесполезен — за
ним никто не придёт. Проверено и остальное поведение,
на котором стоит этот режим (сборка `qwen_code_version: 26.6.31`, вывод `-o json`):

| Что проверяли | Результат |
|---|---|
| Скиллы и MCP в headless | поднимаются: в `init` перечислены инструменты и `mcp_servers` со статусами |
| `--allowed-tools "run_shell_command(python3*)"` на `python3 -c` | выполнено, `auto_accept: 1` |
| То же на `ls /tmp` | **тоже выполнено** — паттерн аргумента не сужает |
| То же без `--allowed-tools` вовсе | выполнено — запуск команд одобряется автоматически |
| `rm -rf /tmp/nope` | отказала **модель**, до слоя разрешений не дошло (`totalCalls: 0`) |

Чего в сборке нет: `--yolo`, `--json-schema`, `--max-tool-calls`, `--max-wall-time`.
Есть: `--max-session-turns`, `--exclude-tools`, `--allowed-mcp-server-names`,
`--system-prompt` / `--append-system-prompt`, `--channel`, `--output-format`.

Отсюда два несущих факта. Первый: **механизма разрешений в автономном режиме нет** — ни
подтверждения, ни рабочего allowlist. Второй: **машинного контракта результата нет** —
`--json-schema` отсутствует, а `result` в выводе это свободный текст модели.

## Goals / Non-Goals

**Goals:**

- Разбор от алерта до вердикта без единого вопроса пользователю.
- Результат, пригодный для машины: обвязка узнаёт исход, не разбирая текст.
- Честный отказ вместо догадки, когда данных не хватает.
- Границы скилла сохранены — но обеспечены тем, чем их в этом режиме можно обеспечить.

**Non-Goals:**

- Обвязка (webhook, cron, CI-job) в поставку скилла не входит. Скилл остаётся директорией,
  которую копируют; демонов он с собой не приносит.
- Автоматические действия по итогам разбора: рестарты, правки, создание тикетов.
- Свой транспорт до систем логов. Как и в диалоговом режиме, используется то, что
  подключено в окружении, плюс переданный путь.
- Обратная связь автору скилла: способ сообщить о расхождении наружу — отдельная работа.
  Здесь расхождение чинится на месте по описанию в `references/`, и этим ограничивается.

## Decisions

### Признак режима — переменная окружения, а не догадка

`INCIDENT_MODE=auto` ставит обвязка. Альтернативы — определять по отсутствию TTY или по
`--channel CI` — отвергнуты: обе делают поведение скилла зависящим от того, как его
случайно запустили. Это то же правило, по которому «сейчас» берётся из `INCIDENT_NOW`, а
не из системных часов: режим разбора должен быть воспроизводим, а не выведен из
обстоятельств. Переменная не разобрана — работает диалоговый режим, как сегодня.

### Отчёт собирает скрипт, а не модель

`triage.py` уже кладёт JSON этапов в `--out`; туда же добавляется `report.json` —
единственный машинный выход режима. Обвязка читает файл, а из stdout берёт только признак
того, что прогон вообще состоялся.

Альтернатива «попросить модель выдать JSON по образцу» отвергнута: контракт, который
держится на форматировании модели, ломается у потребителя и молча. Числа в отчёт кладёт
`confidence.py`, сигнатуры — `parse_logs.py`; модель добавляет формулировки, а не значения.

### «Данных недостаточно» — поле отчёта, а не код возврата

Коды возврата принадлежат клиенту (в наблюдаемом выводе — `FatalCancellationError` с
`code: 130`), и отличить по ним честный отказ разбора от обрыва процесса нельзя. Поэтому
исход живёт в отчёте: `verdict` со значением «данных недостаточно» плюс перечень
недостающего. Отсутствие файла отчёта обвязка трактует как несостоявшийся прогон — это
разные события, и путать их нельзя.

### Каждый вопрос заменяется правилом вывода

| Шаг диалога | Правило автономного режима |
|---|---|
| стенд, сервис, время | из полей алерта; нет полей — вердикт «данных недостаточно» |
| источник логов | переданный путь → карта источников → единственный подходящий; несколько — вердикт, а не выбор наугад |
| расположение базы знаний | только `--kb` или `INCIDENT_KB_DIR`; не задано — разбор идёт, запись не делается |
| следующий шаг | черновик в отчёте; ничего не создаётся |

Правило одно на все четыре: **неопределённость — это исход разбора, а не повод выбрать за
пользователя**. В диалоге неверная догадка стоит одной реплики, здесь её никто не поймает.

### Нормализация алерта — скриптом

`alert_to_incident.py` читает payload Alertmanager / Grafana / Sentry со stdin и отдаёт
карточку и аргументы для `triage.py` (`--stand`, `--service`, окно `--since/--until`).
Разбор известного JSON детерминирован, и поручать его модели незачем: она добавит сюда
только шанс ошибиться. Формат нераспознан — скрипт возвращает ненулевой код, а не
угадывает поля.

### Границы держит среда запуска

Требование «ничего не выполняется без подтверждения» в автономном режиме обеспечить
внутри агента нечем — это показано прогонами, а не предположено. Поэтому в спеке
требование разделяется по режимам, а для автономного вводится другое: **перечень
доступного агенту сужается снаружи**.

Рычаги по убыванию надёжности:

1. изоляция процесса — sandbox, непривилегированный пользователь, read-only монтирование
   рабочего дерева;
2. `--allowed-mcp-server-names` — только источники логов, без трекера (в наблюдаемой
   сессии был подключён `atlassian` со всем набором создания задач и pull request'ов);
3. `--exclude-tools write_file,edit` — убирает инструменты правки;
4. инструкции скилла.

Порядок именно такой, и он не декоративный. Пункт 3 сам по себе косметика: пока доступен
запуск команд — а он нужен, скилл целиком стоит на python3-скриптах, — файл пишется одной
командой оболочки. Пункт 4 влияет на поведение модели (в прогоне она сама отказалась
выполнять `rm -rf`), но зависит от модели и формулировки промпта и гарантией не является.

### Потолок прохода — правило скилла плюс внешний таймаут

Флагов ограничения вызовов в сборке нет. Остаётся `--max-session-turns`, внешний `timeout`
у обвязки и правило «до вывода причины — пять вызовов», которое в этом режиме перестаёт
быть рекомендацией: превышение завершает разбор вердиктом.

### Установка — личная директория скиллов

Автономный профиль ставится в `~/.gigacode/skills/`, а не в проектную `.gigacode/skills/`:
в исходниках родительского форка загрузка проектных скиллов пропускается для недоверенной
директории, а воркер разбирает свежий чекаут. На GigaCode это не прогонялось — до
проверки правило действует как предосторожность, а не как установленный факт.

## Risks / Trade-offs

- **Скилл не активируется: алерт не похож на обращение человека** → профиль запускается с
  `--append-system-prompt`, который включает разбор явно, а не надеется на совпадение по
  `description`.
- **Автономный агент с неограниченным запуском команд на стенде** → режим объявляется
  пригодным только под изоляцией; в документации это записано как условие применения, а не
  как рекомендация. Стенд без изоляции — диалоговый режим.
- **Флаги сужения могут течь так же, как `--allowed-tools`** → `--exclude-tools` и
  `--allowed-mcp-server-names` принимаются только после прогона позитив + негатив. До
  прогона в документации они не называются защитой.
- **Флапающий алерт засоряет базу знаний** → повтор известной сигнатуры идёт через
  обновление записи; новая запись создаётся, когда сигнатура новая.
- **Отчёт с секретами уезжает в чат обвязкой** → отчёт проходит ту же очистку, что запись
  базы знаний и текст тикета; сырые строки логов в него не попадают.
- **Разбор зависит от дня прогона** → `INCIDENT_NOW` ставит обвязка вместе с алертом,
  иначе повторный прогон того же алерта даст другое окно.
- **Поведение проверено на одной сборке** (26.6.31) и одной модели → раздел наблюдений
  датирован и назван версией; расхождение на стенде правится там же, а не по всему тексту.

## Open Questions

- Действительно ли `--exclude-tools` убирает инструмент, а не только скрывает его из
  выдачи?
- Ограничивает ли `--allowed-mcp-server-names` набор реально, и что видит модель, когда
  сервер исключён?
- Доступен ли `--sandbox` на воркерах, где будет жить обвязка (нужен docker или podman)?
- Откуда в `init` берётся `permission_mode: "auto-edit"` без флага — из настроек
  окружения? Если да, профиль обязан задавать режим явно, иначе он меняется вместе с
  машиной.
