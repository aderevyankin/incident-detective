## Why

Скилл заявлен как переносимый — формат Agent Skills общий для нескольких CLI, — но его
содержимое привязано к одной платформе. `SKILL.md` вшивает имена инструментов Qwen Code
(`todo_write`, `ask_user_question`, `run_shell_command`), имя одного из них попало даже в
название требования спеки `incident-detection`, пояснение `$SKILL_DIR` и места поиска
источников логов называют только пути Qwen Code. Между тем скилл нужно разворачивать в
трёх CLI: Qwen Code, Claude Code и GigaCode.

Молчаливая привязка опаснее явного отсутствия поддержки. Обязательный первый шаг разбора —
план работ — назван в спеке через `todo_write`; на платформе, где инструмент называется
иначе, выполнение обязательного требования начинает держаться на догадке модели. Разбор
при этом выглядит нормально, а плана нет.

Установка проблемой больше не является: после `remove-installer` скилл на любой платформе
разворачивается одинаково — копированием `incident-detective/` в её директорию скиллов.
Не хватает только знания, куда именно копировать и как называются инструменты: этому
знанию нужно одно место.

## What Changes

- Реестр платформ в `references/`: назначение инструмента — его имя на каждой платформе,
  личная и проектная директории скиллов, места поиска подключённых MCP-серверов и
  настроек, состояние проверки каждой платформы.
- `SKILL.md` называет инструменты по назначению со ссылкой на реестр вместо вшитых имён.
  Обязательность плана работ и вопроса вариантами при этом не ослабевает.
- **BREAKING** для спеки: требование `incident-detection` «Обязательный план работ через
  `todo_write`» переименовывается — имя платформенного инструмента в названии требования
  делает спеку привязанной к платформе. Поведение скилла не меняется.
- GigaCode вносится третьей платформой. Соответствие принимается полной калькой с Qwen
  Code — каталоги `~/.gigacode/skills` и `.gigacode/skills`, те же имена инструментов,
  настройки в `.gigacode/settings.json` — и помечается в реестре как принятое по
  заявлению, а не проверенное запуском.
- Пояснение `$SKILL_DIR` и места поиска источников логов приводятся по платформам.
- `README.md`: таблица платформ называет директорию скиллов каждой платформы и состояние
  проверки; `openspec/config.yaml` перестаёт называть Qwen Code единственной целевой
  платформой.
- Копирование в несколько платформ размножает базу знаний внутри скилла — README
  указывает на `INCIDENT_KB_DIR` как на способ иметь одну базу на все платформы.
- Платформа объявляется поддерживаемой только после проверки полного разбора на ней.

## Capabilities

### New Capabilities

Нет. Изменение уточняет упаковку и формулировки уже существующих требований.

### Modified Capabilities

- `skill-packaging`: установка перестаёт быть привязанной к одной платформе — появляется
  реестр платформ как единственное место платформенных различий; требование
  платформенно-нейтрального описания инструментов в `SKILL.md`; подтверждение поддержки
  платформы проверкой, а не намерением.
- `incident-detection`: требования о плане работ и о карточке инцидента называют
  инструменты по назначению, а не по имени в Qwen Code.

## Impact

- `incident-detective/references/` — новый реестр платформ; правка `log-sources.md`.
- `incident-detective/SKILL.md` — шаги 0, 1, 9, пояснение `$SKILL_DIR`, шаг 3.1 (поиск
  источников логов).
- `README.md` — таблица поддерживаемых платформ с директориями и состоянием проверки.
- `openspec/config.yaml` — раздел контекста о целевой платформе.
- Предложение `add-claude-code-target` удалено — его содержание целиком поглощено этим
  изменением.

Не затрагивается: скрипты контуров, формат и содержимое базы знаний, поведение разбора,
модель распространения (репозиторием, установка копированием — зафиксирована
`remove-installer`).
