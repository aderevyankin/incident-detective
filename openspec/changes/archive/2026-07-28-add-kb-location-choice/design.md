## Context

`kb_common.kb_dir()` разрешает путь к базе в три шага: флаг `--kb`, переменная
`INCIDENT_KB_DIR`, иначе `$SKILL_DIR/kb`. Механизм переопределения полный, но третий шаг
срабатывает молча, и в результате база почти всегда оказывается внутри скилла — не потому,
что так решили, а потому, что вопрос никогда не задавался.

Отсюда два следствия. Данные лежат в каталоге приложения: `install.sh` вынужден спасать
`INC-*.md` во временную папку при переустановке. И знание остаётся персональным: разбор,
сделанный одним человеком, в команду не попадает.

Простой перенос базы в репозиторий по умолчанию неприемлем — записи содержат фрагменты
логов, а попавшее в git из истории не вычищается. Допустимость этого определяется
политиками, о которых скилл не знает.

Отдельно: очистка записей от секретов и персональных данных — предмет незавершённого
change `add-pii-redaction`, здесь она не трогается. Порядок между ними важен: выпускать
выбор «в проект» раньше усиленной очистки не стоит.

## Goals / Non-Goals

**Goals:**

- Расположение базы становится осознанным выбором, а не молчаливым умолчанием.
- Выбор не мешает разбору инцидента: диалога о хранении в горячий момент нет.
- Директория в репозитории проекта не появляется без согласия пользователя.
- Выбор закрепляется штатным механизмом, без нового формата настроек.
- Выбор, сделанный для проекта, действует в этом проекте, а не в той оболочке, где его
  сделали: инженер, работающий с несколькими проектами, не пишет записи одного в базу другого.

**Non-Goals:**

- Автоматический поиск базы по списку кандидатов — от него отказались в пользу вопроса.
  Проверка одного известного места в текущем репозитории под этот отказ не подпадает: см.
  решение о порядке разрешения пути.
- Собственный файл конфигурации скилла.
- Миграция существующих записей между расположениями.
- Усиление очистки записей — за это отвечает `add-pii-redaction`.
- Слияние нескольких баз при поиске: скилл работает с одной базой за раз.

## Decisions

### Вопрос — при первой записи, а не в начале разбора

Естественное место для вопроса «где база» — начало работы, и это худшее из возможных
мест: инцидент, прод лежит, а скилл спрашивает про хранение. Ранний поиск по базе при этом
и не требует ответа — он читает то, что доступно сейчас.

Первая запись — момент, когда вопрос уместен: разбор закончен, срочность спала, и у
пользователя есть контекст — он видит конкретную запись, которую предлагается куда-то
положить.

### Выбор запоминается через `INCIDENT_KB_DIR`

Хранить выбор нужно вне разбора, и здесь возникает рекурсия: файл состояния сам надо где-то
держать. В проекте — снова пишем в чужой репозиторий; в директории скилла — возвращаем
костыль с сохранением данных при переустановке, от которого и уходим.

Поэтому своего хранилища нет: скилл показывает готовую строку `export INCIDENT_KB_DIR=…`
для shell profile. Механизм уже существует, переживает переустановку скилла и виден
человеку — его можно положить в README проекта или общий dotfile команды.

Плата за это — пользователь может строку проигнорировать, и тогда вопрос повторится при
следующей записи. Приемлемо: повтор происходит в спокойный момент и напоминает о
незакреплённом выборе.

### Выбор в проекте дочитывается из проекта

`INCIDENT_KB_DIR` — одно значение на оболочку, а выбор «в корень проекта» по своей природе
привязан к проекту. Эти две вещи не сходятся, и расхождение между ними даёт худший из
возможных исходов.

Сценарий: инженер разобрал инцидент в проекте A, выбрал «в корень проекта», положил
`export INCIDENT_KB_DIR=~/work/A/memory/knowledgebase` в `~/.zshrc`. Через неделю он
разбирает инцидент в проекте B. Переменная задана — значит, по правилам этого изменения
выбор сделан и вопрос не задаётся. Запись о проекте B уходит в базу проекта A. Молча: ни
предупреждения, ни вопроса, и обнаружится это тогда, когда кто-то будет искать в базе A
чужие инциденты. Ровно та проблема, ради которой базу и выносят в проект, — только теперь
без всякого признака, что она случилась.

Поэтому порядок разрешения пути получает четвёртый шаг: `--kb` → `INCIDENT_KB_DIR` →
база в корне текущего репозитория, **если она там уже существует** → база скилла.

Это не противоречит отказу от автоматического поиска базы по кандидатам. Кандидат ровно
один — известный путь в корне текущего репозитория, — и его существование не догадка, а
прочитанный обратно результат уже сделанного пользователем выбора: директория появляется
только после явного ответа на вопрос. Скилл не ищет, где могла бы быть база; он смотрит, не
выбирали ли уже здесь.

Порядок шагов важен: `INCIDENT_KB_DIR` стоит **выше** базы в проекте. Явно заданная
переменная остаётся сильнее — это способ намеренно работать с одной базой из разных
репозиториев, и отнимать его нельзя. Проект перебивает только умолчание.

Побочно снимается и плата, названная выше: проигнорированная строка `export` больше не
означает, что вопрос повторится. Для проектной базы выбор виден по наличию директории, и
повторно спрашивать не о чем. Строка `export` остаётся нужной для баз вне проекта — там
прочитать выбор неоткуда.

### Путь в проекте — `memory/knowledgebase/`

Директория видимая: база в markdown ради того, чтобы её читал человек без агента, и
скрытый каталог это свойство ослабляет.

Известный риск: имя общее и не говорит, чей это каталог, — если второй инструмент
захочет `memory/`, будет коллизия. Вложенность `knowledgebase/` внутри `memory/` этот риск
частично снимает: соседи занимают соседние подкаталоги, а не спорят за корень.

Корень проекта определяется через `git rev-parse --show-toplevel`, иначе — текущая
директория. Вне репозитория вариант «в корне проекта» предлагается от текущей директории и
предупреждения о git не несёт.

### Вопрос задаёт агент, а скрипт о нём сигнализирует

`kb_add.py` — обычный CLI и спрашивать не может: вопрос задаётся инструментом
`ask_user_question`, то есть агентом. Значит, скрипт должен сообщить, что расположение не
выбрано, а не молча создать базу.

`kb_dir()` начинает возвращать не только путь, но и **источник** — флаг, переменная
окружения или умолчание. При умолчании и пустой базе `kb_add.py` завершается понятным
сообщением «расположение базы не выбрано» и ненулевым кодом; агент по этому сигналу задаёт
вопрос и повторяет запуск уже с `--kb`. Явный `--kb` или `INCIDENT_KB_DIR` работают как
раньше, без вопросов.

### Непустая база в скилле означает, что выбор уже сделан

Если в `$SKILL_DIR/kb` уже лежат записи, спрашивать поздно и бессмысленно: база
существует, и вопрос выглядел бы как предложение бросить её. Признак — наличие `INC-*.md`,
а не самой директории: пустая директория приезжает вместе со скиллом и выбором не является.

### Предупреждение о git — одна строка, без уговоров

Выбран путь внутри репозитория — скилл называет факт: записи попадут в историю и оттуда не
вычищаются. Не отговаривает и не требует подтверждения второй раз. Решение принимает тот,
кто знает политики; задача скилла — чтобы решение было принято со знанием последствий.

## Risks / Trade-offs

- **Вопрос всё равно приходит не вовремя, если разбор короткий** → он привязан к записи, а
  запись делается по согласию пользователя; отказ от записи снимает и вопрос.
- **Строку `export` проигнорируют, вопрос повторится** → повтор в спокойный момент, с
  напоминанием, что выбор не закреплён. Альтернатива — свой файл состояния — хуже.
- **`memory/` может занять другой инструмент** → вложенный `knowledgebase/` уменьшает
  область конфликта; при коллизии остаётся вариант «свой путь».
- **Один человек решает за команду, что логи поедут в git** → предупреждение при выборе;
  полноценно проблема закрывается очисткой записей из `add-pii-redaction`.
- **База проекта перехватывает запись молча.** Директория в корне могла появиться не от
  этого пользователя — прийти с клоном репозитория, где её завёл коллега. Тогда инженер,
  никогда не отвечавший на вопрос о расположении, запишет разбор в общий репозиторий, не
  заметив этого → путь, в который идёт запись, называется в ответе; намеренная работа с
  личной базой закрепляется `INCIDENT_KB_DIR`, которая проект перебивает.
- **Дельта в ту же спеку `knowledge-base`, что и у `add-kb-outcome-tracking`** → требования
  разные (расположение против структуры записи), но при архивации порядок важен: второй
  change нужно синхронизировать после первого, чтобы MODIFIED-блоки не затёрли друг друга.
