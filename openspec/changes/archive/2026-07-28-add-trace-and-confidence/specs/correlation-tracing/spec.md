# correlation-tracing

## ADDED Requirements

### Requirement: Извлечение сквозного идентификатора запроса

Скилл SHALL распознавать correlation id записи по полям `trace_id`, `traceId`,
`traceID`, `request_id`, `requestId`, `requestID`, `correlation_id`,
`correlationId`, `x-request-id`, `rquid`, `rqUID`, `span_id`, `spanId`,
`req_id`, а при их отсутствии — по текстовому шаблону `<имя>=<значение>` в
произвольной строке.

#### Scenario: Идентификатор в структурированной записи

- **WHEN** запись в формате JSON или logfmt содержит одно из перечисленных полей
- **THEN** его значение используется как идентификатор запроса

#### Scenario: Идентификатор в произвольном тексте

- **WHEN** запись не структурирована, но содержит `correlation-id=7f3a-9c` или
  аналогичную пару
- **THEN** значение извлекается по текстовому шаблону

#### Scenario: Идентификатора нет ни в одной записи

- **WHEN** ни в одном источнике не найден сквозной идентификатор
- **THEN** скилл сообщает, что цепочку собрать не из чего
- **AND** называет ожидаемые имена полей
- **AND** предлагает разбор по времени как замену

### Requirement: Сборка цепочки по сервисам

Скилл SHALL сводить записи нескольких источников с одним идентификатором в
цепочку хопов, где хоп — работа одного сервиса. Источник SHALL задаваться в
виде `сервис=путь`, чтобы в выводе стояло имя сервиса, а не имя файла.

#### Scenario: Цепочка через несколько сервисов

- **WHEN** заданы логи нескольких сервисов и идентификатор запроса
- **THEN** выводятся хопы в порядке времени
- **AND** для каждого показаны время первой записи, длительность работы внутри
  сервиса, пауза от предыдущего хопа, худший уровень, число ошибок и HTTP-статусы

#### Scenario: Запрос не найден

- **WHEN** указанный идентификатор не встречается ни в одном источнике
- **THEN** скилл сообщает об этом и завершается ненулевым кодом

#### Scenario: Выбор запроса для разбора

- **WHEN** идентификатор не указан
- **THEN** выводится список запросов, отсортированный по числу ошибок, затем по
  числу задетых сервисов
- **AND** для каждого показаны число записей, набор сервисов и длительность

### Requirement: Определение точки обрыва

Скилл SHALL называть точкой обрыва **самую раннюю по времени** ошибку во всей
цепочке, а не ошибку первого по порядку сервиса.

#### Scenario: Вызывающий сервис пишет ошибку позже вызванного

- **WHEN** payment-api пишет ошибку в 12:31:31.200, а gateway пишет `504` в
  12:31:31.400
- **THEN** точкой обрыва называется payment-api

#### Scenario: Пояснение к точке обрыва

- **WHEN** точка обрыва определена
- **THEN** выводится текст записи
- **AND** поясняется, что ошибки соседних сервисов после этого момента обычно
  являются реакцией, а не отдельной поломкой

#### Scenario: Ошибок в цепочке нет

- **WHEN** ни одна запись цепочки не имеет уровня ERROR или выше
- **THEN** скилл сообщает, что запрос прошёл целиком
- **AND** предполагает, что взят не тот идентификатор либо логи неполные

### Requirement: Узкое место по времени

Скилл SHALL выделять самую долгую паузу между соседними хопами, когда она
составляет не менее секунды.

#### Scenario: Долгое ожидание вызванного сервиса

- **WHEN** между первыми записями двух соседних сервисов прошло 30 секунд
- **THEN** эта пара называется самой долгой паузой с указанием длительности

### Requirement: Расхождение часов между сервисами

Скилл SHALL оценивать расхождение часов по разнице первых отметок общих
запросов и SHALL NOT применять поправку автоматически: сдвиг задаётся
пользователем явно.

#### Scenario: Систематический сдвиг

- **WHEN** разница первых отметок пары сервисов по нескольким запросам держится
  около одного значения при малом разбросе
- **THEN** расхождение помечается как похожее на сдвиг часов
- **AND** выводится готовая поправка в виде флага сдвига

#### Scenario: Разброс велик

- **WHEN** разница между сервисами сильно гуляет от запроса к запросу
- **THEN** это помечается как реальная задержка, а не расхождение часов

#### Scenario: Данных для оценки мало

- **WHEN** общих запросов меньше порога
- **THEN** скилл сообщает, что сравнивать нечего, и не делает выводов

#### Scenario: Применение поправки

- **WHEN** пользователь задал сдвиг для сервиса в секундах
- **THEN** время записей этого сервиса сдвигается на указанную величину
- **AND** сдвиг для неизвестного сервиса считается ошибкой запуска

#### Scenario: Хоп идёт назад во времени

- **WHEN** в цепочке следующий хоп начинается раньше предыдущего
- **THEN** это помечается в выводе
- **AND** предлагается проверить часы и задать поправку

### Requirement: Формат вывода цепочки

Скилл SHALL выдавать цепочку в markdown для чтения человеком и в JSON для
передачи другим скриптам.

#### Scenario: JSON для оценки уверенности

- **WHEN** запрошен формат JSON
- **THEN** вывод содержит идентификатор, хопы с временами и числом ошибок,
  точку обрыва и самую долгую паузу
