## Context

Скилл заканчивается шагом 7 «Вывод» и шагом 8 «Пополни базу знаний». Раздел «Что делать»
внутри вывода — свободная рекомендация текстом, и дальше разбор обрывается: пользователь
сам решает, чинить ли, заводить ли тикет и где.

Одновременно начало разбора (шаг 1, карточка инцидента) устроено как просьба дописать
недостающее текстом одним сообщением. Это дороже для пользователя, чем нужно: стенд, окно
времени и способ передачи логов — закрытые списки.

Обе точки упираются в один инструмент. Qwen Code даёт встроенный `ask_user_question`
(`packages/core/src/tools/askUserQuestion.ts`): 1–4 вопроса за вызов, у каждого 2–4
варианта с подписью и описанием, `header` до 12 символов, свободный ответ («Other»)
пользователю доступен всегда и добавлять его вариантом не нужно. Рекомендуемый вариант
принято ставить первым и помечать в подписи.

Ограничения окружения прежние: никаких новых зависимостей, Python-скрипты только stdlib,
свой MCP-сервер скилл не тащит. Встроенного инструмента для тикетов в Qwen Code нет —
`ToolNames` содержит `edit`, `write_file`, `run_shell_command`, `todo_write`,
`ask_user_question`, `agent` и прочее, но ничего про трекеры.

## Goals / Non-Goals

**Goals:**

- Разбор заканчивается конкретным предложением: правки, баг или задача.
- Ведущий вариант выводится из уровня уверенности, а не из настроения модели.
- Тикет собирается из уже полученного разбора, без повторного опроса.
- Онбординг в начале — выбором из вариантов там, где список закрыт.
- Ни одно действие не выполняется без подтверждения.

**Non-Goals:**

- Не пишем интеграцию с конкретным трекером и не тащим свой MCP-сервер.
- Не добавляем Python-скриптов: изменение целиком в правилах поведения агента.
- Не автоматизируем починку: применение правок остаётся отдельным подтверждённым шагом.
- Не превращаем весь диалог в анкету — свободный ввод остаётся там, где он естественен.

## Decisions

### Предложение следующего шага — через `ask_user_question`, а не текстом

Альтернатива — перечислить варианты в тексте вывода и ждать ответа. Отвергнута: выбор из
трёх взаимоисключающих действий — ровно тот случай, под который инструмент сделан, а
текстовый ответ пришлось бы ещё интерпретировать. Ограничение в 2–4 варианта совпадает с
числом наших вариантов.

Вариант «ничего не делать» отдельным пунктом не добавляется: свободный ответ доступен
всегда, а четвёртый пункт-заглушка съедает место.

### Ведущий вариант выбирается по уровню уверенности из шага 6

`confidence.py` уже даёт три уровня. Связка прямая:

| Уровень | Ведущий вариант | Почему |
|---|---|---|
| подтверждено данными | правки в код | причина установлена, место известно |
| вероятная причина | баг | описание честное, но чинить вслепую рано |
| гипотеза | задача на доисследование | бага с выдуманной причиной быть не должно |

Это продолжение уже принятого в проекте принципа: формулировка вывода зависит от уровня
уверенности, теперь от него же зависит и предлагаемое действие. Альтернатива — всегда
предлагать все три варианта в одном порядке — отвергнута: она перекладывает на
пользователя решение, для которого у скилла есть данные.

Вариант с правками отсутствует, когда место в коде не найдено: предлагать «починить»
нечем.

### Заведение тикета — по той же схеме discovery, что и логи

Порядок: подключённый MCP-сервер трекера → CLI трекера через `run_shell_command`
(`gh issue create`, `jira`, `linear`) → текст тикета для ручного создания. Логика
обнаружения уже описана в `references/log-sources.md`, новый reference повторяет её
подход с другими ключевыми словами (`jira`, `youtrack`, `linear`, `github`, `gitlab`,
`tracker`, `issue`).

Альтернатива — сразу отдавать текст для ручного создания — отвергнута: если трекер
подключён, ручное копирование бессмысленно. Обратная альтернатива, тащить свой MCP, прямо
противоречит принципам проекта.

### Тикет собирается из разбора, а не из нового опроса

К моменту предложения известны карточка, хронология, доказательства, причина, уровень
уверенности и запись базы знаний. Всё это идёт в тикет как есть. Незаполненные поля
остаются пустыми — то же правило, что и в карточке инцидента: не додумывать.

Правила чувствительных данных наследуются от базы знаний без изменений: шаблоны и
точечные строки вместо дампов, токены и ключи не переносятся. Внешний трекер —
публикация наружу, поэтому текст показывается до создания.

### Онбординг вариантами — только там, где список закрыт

Вариантами: стенд, окно времени, способ передачи логов, выбор между несколькими
найденными источниками, выбор сервиса, когда его можно вывести из репозитория или базы
знаний. Свободным вводом: симптом словами пользователя, шаги воспроизведения, путь к
файлу, ссылка, вставка лога.

Граница проходит по тому, откуда берутся варианты. Придумывать список ради формы вредно:
выдуманный список стендов навязывает пользователю чужие названия, а «Other» превращает
вопрос в тот же свободный ввод, только длиннее.

Лимит в 4 вопроса на вызов означает приоритизацию: спрашиваем то, без чего разбор не
двинется (стенд, источник логов), остальное уточняем по ходу.

### Изменение целиком в правилах, без скриптов

Ни одна часть шага не выигрывает от Python: нет ни парсинга, ни агрегации. Новый
reference-файл + шаг в `SKILL.md` + правка стартового плана `todo_write`.

## Risks / Trade-offs

- **Скилл начинает выглядеть как анкета в начале разбора** → вопросы задаются одним
  вызовом, только про закрытые списки, и только когда данных действительно нет в
  сообщении пользователя.
- **Модель предложит завести баг по гипотезе, потому что так проще** → правило привязано
  к уровню из `confidence.py`, а не к усмотрению; в спеке это отдельный запрет.
- **Предложение прочитается как разрешение действовать** → отдельное требование:
  уточняющий вопрос пользователя согласием не считается, текст тикета показывается до
  создания.
- **`ask_user_question` доступен не во всех режимах запуска Qwen Code** (headless,
  неинтерактивный вызов) → правила формулируются как «спрашивай вариантами, где это
  возможно»; при недоступности инструмента остаётся обычный текстовый вопрос, разбор не
  блокируется.
- **CLI трекера может создать тикет не в том проекте** → команда показывается
  пользователю до выполнения, как обычное подтверждаемое действие `run_shell_command`.
- **Разрастание SKILL.md** → детали discovery трекеров и шаблон тикета уходят в
  reference, в SKILL.md остаётся короткий шаг.
