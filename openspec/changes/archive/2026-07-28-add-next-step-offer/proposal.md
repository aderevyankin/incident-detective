## Why

Разбор заканчивается выводом и записью в базу знаний, но результат остаётся висеть в
чате: пользователь сам решает, что с ним делать дальше — чинить, заводить баг или
ставить задачу. Скилл к этому моменту знает больше всех о случившемся (причина, уровень
уверенности, места в коде, предложенный фикс) и может предложить конкретный следующий
шаг вместо того, чтобы обрывать разбор на констатации.

## What Changes

- Новый финальный шаг разбора: после вывода и пополнения базы знаний скилл предлагает
  следующий шаг — решить задачу предложенными изменениями, завести баг или завести задачу.
- Предложение зависит от уровня уверенности: при «подтверждено данными» ведущий вариант —
  фикс, при «гипотезе» — задача на доисследование, а не баг с выдуманной причиной.
- Ни один из вариантов не выполняется молча: правки в код применяются только после
  согласия пользователя, тикет заводится только по его подтверждению.
- Заведение бага/задачи идёт средствами самого Qwen Code (по аналогии с discovery
  источников логов): подключённый MCP-сервер трекера (`/mcp`, `mcpServers` в
  `~/.qwen/settings.json` и `.qwen/settings.json`) либо CLI трекера через
  `run_shell_command` (`gh issue create` и подобное). Ни того, ни другого нет — скилл
  готовит текст тикета для ручного создания. Встроенного инструмента для тикетов в Qwen
  Code нет, поэтому третьего пути не существует.
- Применение фикса идёт встроенными `edit` / `write_file` — и только после согласия.
- Содержимое тикета собирается из уже полученного разбора: симптом, стенд и сервис,
  хронология, доказательства, причина с уровнем уверенности, ссылка на запись базы знаний.
  Секреты и сырые дампы в тикет не попадают на тех же правилах, что и в базу знаний.
- В стартовый план `todo_write` добавляется шаг предложения следующего шага.
- Само предложение задаётся встроенным инструментом `ask_user_question` — выбором из
  вариантов, а не просьбой написать ответ текстом.
- Тем же инструментом ведётся начальный сбор карточки инцидента: стенд, время, источник
  логов и прочее, что укладывается в закрытый список, спрашивается вариантами. Свободный
  ввод остаётся только там, где вариантов не существует, — симптом словами пользователя,
  вставка лога, ссылка на трекер.

## Capabilities

### New Capabilities

Новых capability нет: поведение относится к форме итогового ответа и уже покрывающим её
спекам.

### Modified Capabilities

- `incident-reporting`: добавляется требование о предложении следующего шага по итогам
  разбора, о зависимости предложения от уровня уверенности, о составе тикета и о запрете
  выполнять выбранный вариант без подтверждения пользователя.
- `incident-detection`: стартовый план разбора дополняется шагом предложения следующего
  шага; сбор карточки инцидента ведётся через `ask_user_question` с вариантами вместо
  просьбы ответить текстом.
- `log-ingestion`: выбор источника логов, когда вариантов несколько, предлагается
  через `ask_user_question`.

## Impact

- `incident-triage/SKILL.md`: новый шаг 9 «Следующий шаг», обновлённый стартовый список
  `todo_write`, дополнение раздела «Границы».
- `incident-triage/references/`: новый файл с правилами выбора варианта, discovery
  трекеров и составом тикета.
- `README.md`: описание финального шага и упоминание нового reference-файла.
- Скрипты не затрагиваются: шаг целиком в правилах поведения агента, нового Python-кода и
  зависимостей не появляется.
