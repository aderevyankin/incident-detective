## Context

Аудит подтвердил чтением кода: `kb_add.py:440-441` инкрементирует `reuse_count` и
`reused_at` при любом `--update`, включая чистую смену исхода; `kb_add.py:377-379`
кладёт `--tags`, `--stand` и `services` из `--from-parsed` во фронтматтер без
`scrub_text`, при том что комментарий рядом со `scrub_counts` обещает очистку «по всем
полям записи»; `kb_common.dump_frontmatter:934-935` пропускает пустые списки, и запись
без `--stand`/`--tags` не содержит объявленных обязательными полей `stands`/`tags`;
`confidence.py:260-261` держит одну подсказку `WEAK_HINT['kb']` на все причины слабого
вклада, хотя value < 0.5 достижимо и при найденной записи (непроверенный исход ×0.6,
чужой стенд ×0.6, слабая релевантность).

## Goals / Non-Goals

**Goals:**
- Счётчик переиспользования отражает только повторы инцидента, как объявляет спека.
- Ни одно значение не попадает во фронтматтер мимо общей функции очистки.
- Обязательные поля фронтматтера присутствуют в каждой записи инцидента.
- Подсказки уверенности сообщают действительную причину слабого вклада базы знаний.

**Non-Goals:**
- Новые флаги, изменение формата выдачи `kb_search`/`confidence` — контракты не меняются.
- Пересмотр весов и коэффициентов уверенности (0.6 за исход и стенд остаются как есть).
- Ретроактивная правка существующих записей базы: старые записи без `stands`/`tags`
  читаются как прежде (пустые списки по умолчанию).

## Decisions

- **Критерий повтора для `reuse_count`: обновление несёт свидетельство повтора.**
  Инкремент выполняется, когда `--update` сопровождается хотя бы одним из: `--signature`,
  `--from-parsed`, `--stand`, текстом разделов разбора (`--symptoms`, `--diagnosis`,
  `--root-cause`, `--fix`, `--verify`, `--distinguishing`, `--notes`) — то есть в записи
  появляются следы нового случая. Автоподхват по совпавшей сигнатуре в автономном режиме
  (`find_by_signature`) — повтор по определению, инкремент сохраняется. Чистая правка
  карточки — только `--outcome`/`--status`/`--severity`/`--tags`/`--title`/`--related`/
  `--file`/`--commit` — счётчик и `reused_at` не трогает.
  Альтернатива «инкремент только при `--outcome confirmed`» отклонена: подтверждение
  исхода и повтор инцидента — независимые события; повтор чаще фиксируется вообще без
  `--outcome`, а привязка к нему сломала бы сценарий «Повтор известного инцидента».
  Заметка «Повторилось <дата>» в разделе «Заметки» подчиняется тому же критерию: она и
  сейчас пишется только при обновлении без текста, а с новым условием перестаёт
  появляться от чистой смены исхода.
- **Очистка полей — в точке сбора значений, той же функцией `scrub`.** `split_csv(args.tags)`,
  `split_csv(args.stand)` и сервисы из `--from-parsed` проходят через `scrub(...,
  scrub_counts)` до попадания в `meta` — и в ветке создания, и в ветке обновления.
  Отдельной реализации очистки не появляется (спека это прямо запрещает); счётчик
  срабатываний остаётся общим, чтобы предупреждение «очистка сработала» охватывало и
  эти поля. Альтернатива — чистить внутри `dump_frontmatter` — отклонена: очистка на
  выходе маскировала бы значения и в записях карты источников, где адреса и запросы —
  легитимные данные, и размазала бы ответственность между модулями.
- **Обязательные поля пишутся всегда; спека не ослабляется.** В `dump_frontmatter`
  вводится перечень полей, которые не выпадают при пустом значении: `stands`, `tags` —
  пустой список пишется явно (`stands: []`). Прочие списочные поля (`files`, `commits`,
  `related`, `signatures`, `services`) по-прежнему опускаются пустыми — спека числит их
  необязательными, и шум из пустых ключей записи не нужен. Выбор «чинить код, а не
  спеку» обоснован: обязательность `stands`/`tags` — осознанное решение (поиск и фильтры
  опираются на эти поля), а их молчаливое отсутствие уже маскировало расхождение.
  Существующие записи без этих полей продолжают читаться: парсер фронтматтера трактует
  отсутствие как пустой список, миграция не нужна.
- **Подсказка контура базы — три правды вместо одной.** `score_kb` уже знает причину
  слабости; подсказка строится от неё, а не от одного словаря `WEAK_HINT['kb']`:
  совпадений нет → прежний текст «запиши этот случай»; запись найдена, вклад снижен
  непроверенным исходом → «подтверди исход записи <id>» (согласуется с уже существующим
  сценарием «Подсказка по укреплению вывода» требования о вкладе базы); вклад снижен
  чужим стендом/сервисом → «сверь условия: запись с другого стенда, совпадение может
  быть внешним». Механика: `score_kb` кладёт готовую подсказку в свой результат
  (например, ключ `hint`), а рендер использует её вместо статического `WEAK_HINT['kb']`,
  сохраняя словарь для остальных контуров. Альтернатива — вычислять причину заново в
  рендере по notes/warnings — отклонена: парсинг собственных человекочитаемых строк
  хрупок, причина известна в момент оценки.

## Risks / Trade-offs

- [Существующие базы уже накрутили `reuse_count` сменами исхода] → счётчики не
  пересчитываются задним числом: история неразличима, а счётчик — вспомогательная
  метка выдачи, в релевантность он не входит (спека это фиксирует).
- [Явное `stands: []` изменит эталоны тестов записи] → правятся только эталоны,
  фиксировавшие отсутствие обязательных полей, каждый — с объяснением.
- [Очистка тегов/стендов заденет легитимные значения с цифрами] → используется та же
  общая функция, что для текстов: её правила уже откалиброваны, отдельных паттернов
  для коротких полей не вводится; счётчик срабатываний покажет факт очистки в выводе.
- [Изменение структуры результата `score_kb` (ключ `hint`)] → ключ добавляется, ничего
  не удаляется; JSON-вывод расширяется совместимо.

## Migration Plan

Правки самодостаточны, флаги и форматы не меняются, миграция базы не требуется.
Порядок: сначала регресс-тест на каждый пункт (красный), затем правка (зелёный).
Откат — реверт коммита изменения целиком.
