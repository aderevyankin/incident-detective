## Context

Аудит подтверждён чтением и прогоном (174 теста зелёные). Центральный разрыв:
спека performance-budgets утверждает «Бюджеты SHALL проверяться бенчмарком, а не
оцениваться на глаз», но `tools/bench.py` не вызывается ни из `tests/run.py`, ни
из `.github/workflows/checks.yml` — CI гоняет только `python3 tests/run.py`.
Единственный автоматический замер — `tests/test_source_map.py::
SearchBudgetWithSourceMap` на урезанном входе. Это не случайность: README
осознанно объясняет, что строгие числа зависят от машины и в CI дадут ложные
падения. Остальные находки — тесты, не дотянутые до собственных спек: негативные
сценарии bench, самопроверка `tools/check_docs.py` (регрессия в `FENCE_RE` молча
отключит всю проверку документации — `run_command_blocks` не проверяет, что хоть
один блок исполнен), `INCIDENT_NOW` не для всех скриптов, дефолт
`MAX_SUMMARY_CHARS = 12000` (`kb_common.py:78`) без теста, телеметрия без
оркестратора, недоассерченные `test_robustness.py` и `test_kb_outcomes.py`.

## Goals / Non-Goals

**Goals:**
- Спека и практика проверки бюджетов согласованы: понятно, что проверяется
  автоматически, что — руками, и когда ручной прогон обязателен.
- Ни одна проверка обвязки не может отключиться молча: у инструментов проверки
  есть собственные тесты и нижняя граница исполненного.
- Требования спек, объявленные «для всех скриптов», покрыты тестами для всех
  скриптов.

**Non-Goals:**
- Изменение самих бюджетов, эталонного входа или измеряемого набора скриптов.
- Строгие бюджеты в CI — осознанное решение «числа зависят от машины» остаётся.
- Правки поведения скриптов `incident-detective/scripts/` — только обвязка;
  единственное исключение: флаг множителя в `tools/bench.py` (инструмент
  разработки, не скилл).

## Decisions

- **Бенчмарк в CI: отдельный блокирующий smoke-job с щадящим порогом, строгий
  прогон остаётся ручным пунктом приёмки.** Рассмотрены три варианта:
  (а) строгие бюджеты в CI — отклонено: README прав, машины CI медленные и
  разные, ложные падения обесценят job; (б) только зафиксировать в спеке ручной
  прогон — отклонено: «SHALL проверяться бенчмарком» без единого автоматического
  запуска означает, что сломанный или замедлившийся на порядок скрипт доедет до
  main незамеченным; (в) двухъярусная схема — принято. CI ловит регрессии
  масштаба «в разы», строгие числа сверяются на типовой рабочей машине, как
  спека и трактует бюджеты («порог для типовой рабочей машины, а не гарантия»).
  Job делается блокирующим, а не informational: порог с множителем и так щедрый,
  а неблокирующие job'ы перестают читать через неделю.
- **Щадящий порог — множитель бюджета, а не отдельная таблица.** `tools/bench.py`
  получает флаг вида `--budget-scale N` (точное имя — за реализацией): вердикт
  по `budget × N` для «≤», `budget / N` для «≥» (строк/с). Одна таблица
  бюджетов остаётся единственным источником правды; вторая таблица «для CI»
  разошлась бы с первой. Значение множителя для CI — ориентир 3; фиксируется в
  workflow с комментарием, спека числа не нормирует.
- **Smoke-job гоняет тот же эталонный вход, одну версию Python.** Урезать вход
  нельзя: бюджеты parse_logs заданы в строках/с на входе 400 000 строк, меньший
  вход меняет профиль. Матрица версий не нужна — совместимость проверяет
  основной job; бенчмарку достаточно современного Python.
- **Самопроверка check_docs живёт в test-harness, реализуется двумя слоями.**
  Слой 1: юнит-тесты экстрактора (`extract_blocks`, `resolve_structure_paths`,
  skip-маркеры) на подготовленном markdown-тексте — ловят изменение правил
  извлечения. Слой 2: нижняя граница «в README исполнено ≥ N блоков» — ловит
  регрессию на живом документе, даже если юнит-тесты обошли её стороной.
  N выбирается заметно ниже текущего числа блоков (например, половина), чтобы
  удаление пары блоков из README не роняло прогон; счётчик исполненных блоков
  возвращается из `run_command_blocks` или читается из его вывода — за
  реализацией. Дельта кладётся в test-harness («Обязательные классы проверок»),
  а не в project-documentation: там описано, ЧТО проверяется в документации,
  здесь — что сами проверки не выключаются молча; это свойство прогона.
- **Недостающие тесты пишутся к существующим требованиям — без новых дельт.**
  `INCIDENT_NOW` для `trace.py`/`confidence.py`/`kb_add.py`/`triage.py`
  (сценарий «Значение не разобрано» уже требует этого от всех), дефолт
  `MAX_SUMMARY_CHARS` (требование «не более 12 000 символов» уже есть),
  телеметрия `triage.py` (сценарий «Видно, какие контуры прогнаны» — это как раз
  оркестратор), негативные сценарии bench (оба уже в спеке). Спеки не меняются —
  меняется покрытие.
- **Точечные ассерты вместо новых тестов там, где тест уже есть.**
  `test_robustness.py`: к существующему тесту triage с пустым не-git `--repo`
  добавляется ассерт, что в сводке назван непройденный контур кода (сценарий
  «Этап не дал результата» это требует). `test_kb_outcomes.py::
  test_reuse_count_does_not_affect_relevance`: тест приводится к собственному
  комментарию — счёт запрашивается при `reuse_count` 0 и 40 и сравнивается.

## Risks / Trade-offs

- [Smoke-job всё же флапнет на аномально медленном раннере] → множитель
  подобран по фактическим замерам раннера до включения блокировки; при флапе
  первым делом поднимается множитель, а не выключается job.
- [Щадящий порог пропустит деградацию в 1.5–2 раза] → осознанно: её ловит
  строгий ручной прогон, который дельта спеки делает обязательным пунктом
  приёмки изменений, задевающих измеряемые скрипты (в задачах fix-parsing-and-time
  такой пункт уже есть — практика закрепляется, а не изобретается).
- [Нижняя граница N блоков в README закаменеет и начнёт мешать реструктуризации
  README] → N закладывается с запасом вниз и правится в том же изменении, что
  реструктурирует README; проверка называет фактическое и требуемое число.
- [Дополнительный job удлиняет CI] → бенчмарк укладывается в минуты
  (генерация входа + 6 замеров), job идёт параллельно основному.
- [Усиленный ассерт reuse_count может вскрыть, что счёт всё же зависит от
  счётчика] → тогда это находка о поведении `kb_search`, разбирается отдельным
  изменением, а не подгонкой ассерта.

## Migration Plan

Изменение самодостаточно: сначала тесты к существующему поведению (зелёные сразу,
кроме вскрывающих реальные дефекты), затем флаг множителя в bench, затем job в
workflow. Откат — реверт коммита; поведение скилла не затрагивается.
