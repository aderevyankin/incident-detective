## Context

Формат Agent Skills — директория с `SKILL.md` и YAML-фронтматтером — общий для обеих платформ,
и это главное, что делает поддержку дешёвой: переносить нужно упаковку и обвязку, а не содержание.

Различается три вещи:

1. **Куда ставить.** `install.sh:15-20` знает `~/.qwen/skills` и `./.qwen/skills`. У Claude Code
   свои директории личных и проектных скиллов.
2. **Как называются инструменты.** `SKILL.md` вшивает `todo_write` (шаг 0), `ask_user_question`
   (шаг 1), `run_shell_command` (шаг 9). Имена подняты в спеки: требование `incident-detection`
   называется «Обязательный план работ через `todo_write`».
3. **Где искать подключённые серверы.** `SKILL.md:119-120` называет `/mcp`, `.qwen/settings.json`,
   `~/.qwen/settings.json`.

Скрипты платформенно нейтральны: чистый Python из stdlib, запускаются одинаково. База знаний тоже:
markdown плюс индекс.

## Goals / Non-Goals

**Goals:**

- Скилл ставится и работает на обеих платформах без правки его содержимого руками.
- Обязательные действия скилла — план работ, вопрос с вариантами — выполняются на обеих
  платформах, а не полагаются на догадку модели об имени инструмента.
- `README.md` перестаёт обещать то, чего нет.
- Добавление третьей платформы позже не требует переписывать `SKILL.md`.

**Non-Goals:**

- Абстракция над различиями платформ в коде: обёртки, адаптеры, слой совместимости. Различия
  описываются текстом, а не кодом.
- Поддержка платформ, на которых нет формата Agent Skills.
- Изменение поведения скриптов и базы знаний.
- Изменение оснастки OpenSpec в `.claude/` и `.qwen/`: это инструменты разработки проекта.
- Раздельные базы знаний по платформам.

## Decisions

### Инструменты описываются по назначению, имена — в справочнике

`SKILL.md` говорит «инструмент ведения списка задач» и «инструмент вопроса с вариантами
ответа», а таблица соответствия имён по платформам живёт в отдельном файле `references/`.

Альтернатива «перечислять оба имени в каждом упоминании» отвергнута: упоминаний много, текст
раздувается, а третья платформа потребует пройти по всем. Альтернатива «оставить имена Qwen Code
и понадеяться, что модель догадается» отвергнута по существу требования: план работ объявлен
обязательным первым действием, и его выполнение не может держаться на догадке.

Важно, что меняется формулировка, а не требование. «Первым действием создай список задач» остаётся
обязательным; меняется только то, что инструмент называется по роли.

Требование в спеке `incident-detection` переименовывается соответственно — имя платформенного
инструмента в названии требования делает спеку привязанной к платформе.

### Платформа выбирается явно, а по умолчанию — определяется и объявляется

Установщик принимает явное указание платформы. Без указания он смотрит, директории каких платформ
существуют, и объявляет свой выбор до копирования.

Молчаливый выбор здесь недопустим: пользователь, у которого есть обе платформы, иначе узнает о
том, куда встал скилл, только когда тот не запустится там, где ожидался.

Если найдены обе платформы и явного указания нет — установщик сообщает об этом и предлагает
поставить в обе. Команды работают в разных средах, и одна база знаний на обе — нормальный
сценарий, а не исключение.

### Одна поставка, а не отдельная сборка под платформу

Копируется одна и та же директория скилла. Различия — в путях установки и в справочнике
соответствий, а не в содержимом. Две сборки означали бы две версии `SKILL.md`, которые разойдутся:
правку внесут в одну, а проверят на другой.

Плата: справочник соответствий едет в поставке на обе платформы, и на каждой из них половина
таблицы лишняя. Это дешевле расхождения.

### `$SKILL_DIR` поясняется по платформам

Обозначение `$SKILL_DIR` в командах остаётся — оно и вводилось как раз для того, чтобы не вшивать
путь. Меняется пояснение: вместо одного пути Qwen Code приводятся пути обеих платформ.

### Поддержка объявляется после проверки, а не после написания кода

Платформа считается поддержанной, когда на ней пройден разбор целиком: самозапуск по описанию
инцидента, план работ, вопрос с вариантами, запуск скриптов, пополнение базы знаний. Каждый из
этих шагов задействует платформенный механизм, и ни один не проверяется чтением кода установщика.

Это не формальность: самозапуск зависит от того, как платформа читает `description`, — то есть от
того, что нельзя проверить иначе, чем запуском.

## Risks / Trade-offs

- **Риск: расхождение поведения платформ.** Инструменты называются по-разному не только именем —
  различаются и их возможности, например состав полей задачи или формат вопроса с вариантами.
  Смягчение: справочник фиксирует не только имена, но и замеченные отличия; проверка выполняется
  на обеих платформах.
- **Риск: справочник устареет.** Имена инструментов меняются на стороне платформ. Смягчение:
  справочник — один файл, и он назван местом, где это чинится.
- **Риск: описание по назначению окажется расплывчатым** и модель выберет не тот инструмент.
  Смягчение: описание сопровождается прямой отсылкой к справочнику, где имена перечислены точно.
- **Trade-off: текст `SKILL.md` становится чуть менее конкретным.** Принято ради того, чтобы
  требование выполнялось на обеих платформах, а не выглядело выполненным на одной.
