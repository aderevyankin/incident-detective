## Context

README вырос до 320 строк без заданной структуры. Разделы добавлялись по мере появления
возможностей: скорость, требования к окружению, воспроизводимость, проверки, спецификация.
Каждый по отдельности осмыслен, но вместе они отвечают на вопросы в порядке, обратном тому, в
каком их задают: сначала устройство и бюджеты, потом установка, и нигде — как это выглядит в
работе.

Материал для сквозного примера в репозитории уже есть. `tests/fixtures/logs/` содержит
синтетические логи, `tests/expected/` — заранее известный верный ответ по каждому. Это редкое
удобство: документация может показывать настоящий вывод, а не выдуманный, и читатель может
его воспроизвести.

Ограничение по языку и стилю задано проектом: русский, технические идентификаторы в оригинале.

## Goals / Non-Goals

**Goals:**

- Читатель за пять минут понимает, что делает скилл, и видит его в работе на своих данных или
  на фикстурах.
- README отвечает на вопросы в порядке их появления: что это → как поставить → как выглядит
  разбор → подробности.
- Устаревание README обнаруживается проверкой, а не глазами.
- Понятно, какое изменение обязано поправить README, а какое нет.

**Non-Goals:**

- Перенос содержания `SKILL.md` или `references/` в README. Это документация для человека, а
  не вторая копия инструкций для модели.
- Порождение README из спецификаций. Спека описывает требования, README — способ ими
  пользоваться; это разные тексты.
- Сайт документации, версионирование документации, перевод на другие языки.
- Изменение поведения скилла.

## Decisions

### Заданная структура вместо накопления разделов

README получает фиксированный порядок разделов, и каждый отвечает на один вопрос читателя:

1. Что это и какую задачу решает — абзац, без устройства.
2. Быстрый старт — установка и первый запуск.
3. Как это выглядит — короткий пример разбора со ссылкой на `docs/walkthrough.md`.
4. Поддерживаемые платформы — с состоянием проверки.
5. Требования к окружению и ограниченный режим.
6. Устройство: три контура, сигнатура, уверенность.
7. Скрипты отдельно от агента.
8. База знаний.
9. Разработка: проверки, бюджеты, воспроизводимость, спецификация.
10. Границы.

Порядок именно такой, потому что нынешний README ставит раздел «Про скорость» третьим — до
установки. Числа бюджетов важны для того, кто скилл уже выбрал, а не для того, кто на него
смотрит впервые.

Альтернатива «разбить README на несколько файлов и оставить оглавление» отвергнута для проекта
такого размера: один файл, который читается сверху вниз, лучше пяти, между которыми нужно
ходить. Выносится только walkthrough — он длинный и линейный.

### Walkthrough на фикстурах, а не на выдуманном логе

`docs/walkthrough.md` показывает разбор целиком: вставленный стектрейс, план работ, запуск
`triage.py` на фикстуре, сводка, совпадение в базе знаний, уровень уверенности, вывод,
предложение следующего шага, запись в базу.

Все команды выполняются на файлах из `tests/fixtures/`, поэтому вывод в документе — настоящий,
и читатель получает такой же. Выдуманный пример этого свойства не имеет и вдобавок устаревает
незаметно.

Плата: walkthrough придётся обновлять при изменении формата вывода. Это приемлемо — и это же
причина, по которой команды из документа входят в проверку.

### README проверяется тем же прогоном, что и код

`tools/check_docs.py` проверяет три вещи, каждая из которых уже ломалась или сломается:

- команды из блоков кода запускаются и завершаются нулевым кодом (кроме помеченных как
  требующие внешнего окружения);
- перечень capability в таблице совпадает с содержимым `openspec/specs/`;
- дерево файлов в разделе «Структура» совпадает с тем, что лежит в репозитории.

Числа бюджетов скорости не проверяются на совпадение с замером: они меняются от машины к
машине, и это работа `tools/bench.py`. Проверяется только то, что таблица бюджетов ссылается
на существующие замеры.

Альтернатива «порождать разделы README скриптом» отвергнута: порождённый текст читается как
порождённый, а README — единственное место, где проект говорит человеческим голосом.

### Правило обновления формулируется через повод, а не через призыв

«Держите README в актуальном состоянии» ничего не значит. Вместо этого перечисляются поводы:
меняется установка, состав скриптов или их флаги, перечень capability, числовые бюджеты,
требования к окружению, границы дозволенного. Изменение с таким поводом правит README в своём
составе, и это входит в его задачи.

Изменения без такого повода README не трогают — это тоже часть правила, иначе каждое
предложение будет дописывать себе абзац.

## Risks / Trade-offs

**Проверка команд в README станет медленной или хрупкой** → Проверяются только команды,
работающие на фикстурах репозитория. Всё, что требует внешнего окружения — установка в
директорию платформы, обращение к MCP-источнику, — помечается в документе и в проверке
пропускается.

**Walkthrough устареет при смене формата вывода** → Его команды входят в ту же проверку.
Расхождение обнаруживается прогоном, а не читателем.

**Конфликты с параллельной работой над README** → Изменение идёт последним из трёх, трогающих
файл, и вбирает уже внесённые правки. Задача сверки стоит явно.

**Сокращение README потеряет нужное** → Ничего не удаляется без переноса: каждый вынесенный
кусок получает адрес в `docs/` или `references/`, и на него остаётся ссылка.

## Open Questions

- Нужен ли `docs/walkthrough.md` внутри устанавливаемого скилла. Пока нет: он для человека,
  выбирающего скилл, а не для модели во время разбора, и объём поставки увеличивать незачем.
- Достаточно ли существующих фикстур для сквозного разбора со всеми тремя контурами — контур
  кода требует git-репозитория с историей. Выясняется при написании walkthrough; при нехватке
  добавляется подготовленная фикстура.
