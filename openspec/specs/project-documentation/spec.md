# project-documentation Specification

## Purpose
README и сопутствующая документация репозитория остаются согласованными с фактическим
поведением скилла: структура README, честный перечень поддерживаемых платформ, сквозной
пример разбора на реальных фикстурах и автоматическая проверка, что описанное в тексте
(команды, таблица capability, дерево файлов) не разошлось с репозиторием.
## Requirements
### Requirement: Состав и порядок README

`README.md` SHALL отвечать на вопросы читателя в порядке их появления: что это, как поставить,
как выглядит работа, подробности. Разделы про устройство, бюджеты скорости и разработку SHALL
следовать после установки и примера работы, а не предшествовать им.

#### Scenario: Первый раздел объясняет назначение

- **WHEN** README открыт впервые
- **THEN** первый раздел говорит, какую задачу решает скилл
- **AND** не начинается с устройства, бюджетов или требований

#### Scenario: Установка предшествует подробностям

- **WHEN** читатель ищет, как поставить скилл
- **THEN** раздел установки находится до разделов об устройстве и о разработке

#### Scenario: Пример работы присутствует

- **WHEN** читатель хочет понять, как выглядит разбор
- **THEN** README содержит короткий пример и ссылку на сквозной разбор
- **AND** пример показывает и ввод пользователя, и ответ скилла

#### Scenario: Точка входа остаётся обозримой

- **WHEN** подробность занимает больше нескольких абзацев
- **THEN** она выносится в отдельный документ, а в README остаётся ссылка

### Requirement: README не привязан к одной платформе

`README.md` SHALL описывать установку и запуск для каждой поддерживаемой платформы. Примеры
команд SHALL NOT содержать путь установки одной платформы там, где команда одинакова для всех.

#### Scenario: Установка приведена для каждой платформы

- **WHEN** читатель ищет команду установки
- **THEN** приведён способ выбрать платформу
- **AND** ни одна платформа не выдаётся за единственную

#### Scenario: Примеры запуска скриптов платформенно нейтральны

- **WHEN** README показывает запуск скрипта вне агента
- **THEN** путь обозначается как `$SKILL_DIR`
- **AND** пояснение к обозначению даётся один раз

#### Scenario: Состояние проверки платформы названо

- **WHEN** README перечисляет поддерживаемые платформы
- **THEN** по каждой указано, проверялся ли на ней полный разбор

### Requirement: Установка описана как получение репозитория и копирование

`README.md` SHALL описывать установку без скрипта установки: получить репозиторий —
клонированием, выгрузкой или передачей ссылки на него своему AI-ассистенту — и
скопировать `incident-detective/` в директорию скиллов платформы. README SHALL NOT
содержать жёсткий URL внутреннего репозитория. README SHALL предупреждать о судьбе
записей базы знаний при обновлении копированием поверх существующей установки.

#### Scenario: Установка без скрипта

- **WHEN** читатель ищет способ установки
- **THEN** README предлагает клонировать репозиторий или дать ссылку на него своему
  AI-ассистенту
- **AND** установка сводится к копированию `incident-detective/` в директорию скиллов
  платформы и перезапуску CLI

#### Scenario: Обновление поверх существующей установки

- **WHEN** README описывает обновление уже установленного скилла
- **THEN** сказано, что копирование затирает базу знаний внутри директории скилла
- **AND** рядом названы способы сохранить записи: внешнее расположение базы или ручное
  сохранение `INC-*.md`

### Requirement: Сквозной разбор в документации

Репозиторий SHALL содержать документ со сквозным разбором инцидента от исходного сообщения
пользователя до записи в базу знаний. Все команды документа SHALL выполняться на материалах
репозитория, чтобы читатель мог повторить их и получить тот же вывод.

#### Scenario: Разбор показан целиком

- **WHEN** читатель открывает сквозной разбор
- **THEN** показаны сообщение пользователя, план работ, запуск разбора, сводка, совпадение в
  базе знаний, уровень уверенности, вывод и предложение следующего шага

#### Scenario: Команды воспроизводимы

- **WHEN** читатель выполняет команды документа у себя
- **THEN** используются файлы из репозитория
- **AND** полученный вывод совпадает с приведённым

#### Scenario: Вывод настоящий

- **WHEN** в документ включается вывод скрипта
- **THEN** он получен запуском, а не составлен вручную

### Requirement: Проверка актуальности документации

Репозиторий SHALL содержать проверку, обнаруживающую расхождение документации с содержимым
репозитория. Проверка SHALL входить в общий прогон и SHALL возвращать ненулевой код при
расхождении.

#### Scenario: Команды из документации запускаются

- **WHEN** выполняется проверка документации
- **THEN** команды из блоков кода запускаются
- **AND** завершение с ненулевым кодом считается расхождением

#### Scenario: Команда требует внешнего окружения

- **WHEN** команда требует установленной платформы, сети или внешнего источника логов
- **THEN** она помечена в документе как таковая
- **AND** проверкой пропускается

#### Scenario: Перечень capability сверяется со спецификацией

- **WHEN** README перечисляет capability проекта
- **THEN** перечень сверяется с содержимым `openspec/specs/`
- **AND** расхождение приводит к ненулевому коду

#### Scenario: Дерево файлов сверяется с репозиторием

- **WHEN** README показывает структуру директорий
- **THEN** перечисленные файлы сверяются с существующими
- **AND** расхождение приводит к ненулевому коду

#### Scenario: Проверка входит в общий прогон

- **WHEN** запускается общий прогон проверок репозитория
- **THEN** проверка документации выполняется вместе с остальными

### Requirement: Повод обновить документацию

Изменение, затрагивающее установку, состав скриптов и их флаги, перечень capability, числовые
бюджеты, требования к окружению или границы дозволенного, SHALL обновлять `README.md` в своём
составе. Изменение без такого повода SHALL NOT дописывать в README собственный раздел.

#### Scenario: Изменение меняет установку

- **WHEN** меняется способ установки или перечень платформ
- **THEN** соответствующий раздел README правится в том же изменении

#### Scenario: Появился новый скрипт

- **WHEN** в скилл добавляется скрипт или меняются флаги существующего
- **THEN** README и проверка документации приводятся в соответствие в том же изменении

#### Scenario: Повода нет

- **WHEN** изменение затрагивает только внутреннее поведение скриптов
- **THEN** README не правится

#### Scenario: Числовое утверждение подкреплено

- **WHEN** README приводит числовой бюджет или замер
- **THEN** назван инструмент, которым это число получается
