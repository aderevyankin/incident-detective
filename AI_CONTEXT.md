# AI_CONTEXT

Контекст репозитория для агентов. `AGENTS.md` и `GIGACODE.md` — симлинки на этот файл.

## Что это за проект

`incident-detective` — скилл разбора багов и инцидентов в формате [Agent Skills](https://qwenlm.github.io/qwen-code-docs/en/users/features/skills/):
директория со `SKILL.md`, YAML-фронтматтером и вспомогательными файлами. Целевая
платформа — **GigaCode CLI**; разработка и прогоны идут на Qwen Code. GigaCode устроен
как полная калька Qwen Code — те же имена инструментов, те же файлы настроек — и
отличается только корневым каталогом: `.gigacode/` вместо `.qwen/` (`~/.gigacode/skills/`,
`.gigacode/skills/`, `.gigacode/settings.json`). При расхождении приоритет у GigaCode.

Разбор идёт по трём контурам, и связывает их **сигнатура** — устойчивый отпечаток ошибки
(класс исключения, HTTP-статус, шаблон сообщения):

| Контур | Вопрос | Скрипты |
|---|---|---|
| База знаний | Мы это уже видели? Откуда брать логи? | `kb_search.py`, `kb_add.py`, `kb_index.py` |
| Логи | Что происходило на самом деле? | `parse_logs.py`, `timeline.py`, `trace.py` |
| Код | Где ломается и из-за чего? | `code_hints.py` |

Типовой разбор проходит все три одной командой — `triage.py`. `confidence.py` считает,
на скольких контурах стоит вывод, и переводит это в уровень: подтверждено данными /
вероятная причина / гипотеза.

**Два режима запуска.** Диалоговый — по умолчанию. Автономный (`INCIDENT_MODE=auto`) —
разбор от алерта, без человека в контуре: вопросов нет, вход даёт
`alert_to_incident.py`, выход — `report.json` в директории `--out`. Правила режима —
`incident-detective/references/aiops.md`, состав отчёта —
`incident-detective/templates/aiops-report.md`.

Продукт здесь — не только код. Половина поведения задана инструкциями в `SKILL.md`, и
правки в них — такая же работа, как правки в скриптах.

## Раскладка

```
incident-detective/           сам скилл — то, что копируется пользователю
  SKILL.md                 инструкции агенту: когда включаться, порядок шагов, границы
  scripts/*.py             исполняемая часть, запускается как процессы
    triage.py              оркестратор трёх контуров; он же собирает report.json
    alert_to_incident.py   алерт Alertmanager/Grafana/Sentry → карточка инцидента
  references/*.md          подробности, на которые SKILL.md ссылается по ходу
    aiops.md               автономный режим: правила вывода, среда запуска, расхождения
  templates/*.md           шаблоны записи, постмортема, пример записи базы
    aiops-report.md        состав полей машинного отчёта
  kb/                      база знаний по умолчанию — пуста, пока выбор не сделан
                           две разновидности записей: INC-* разборы, SRC-* карта источников
tests/                     проверки скриптов; run.py — единственная точка входа
tools/bench.py             бюджеты скорости
tools/check_compat.py      разбираются ли скрипты минимальной версией Python
openspec/                  спеки и предложения по изменениям
.claude/ .qwen/            оснастка разработки (команды и скиллы OpenSpec), не поставка скилла
README.md                  вход в проект для человека
AI_CONTEXT.md              этот файл; AGENTS.md и GIGACODE.md — симлинки на него
```

## Команды

```bash
python3 tests/run.py              весь набор проверок (плюс проверка совместимости)
python3 tests/run.py test_parse   один файл проверок
python3 tools/bench.py            бюджеты скорости, ненулевой код при нарушении
npx @fission-ai/openspec@latest validate --specs --strict   спеки

# автономный разбор целиком, на фикстурах репозитория
python3 incident-detective/scripts/alert_to_incident.py \
  --file tests/fixtures/alerts/alertmanager.json > /tmp/run/incident.json
INCIDENT_MODE=auto python3 incident-detective/scripts/triage.py \
  tests/fixtures/logs/payment.log --incident /tmp/run/incident.json \
  --kb tests/fixtures/kb --repo . --out /tmp/run     # → /tmp/run/report.json
```

Установщика нет: скилл разворачивается копированием `incident-detective/` в директорию
скиллов платформы — репозиторий клонируют или дают ссылку на него AI-ассистенту.

CI (`.github/workflows/checks.yml`) гоняет `tests/run.py` на **Python 3.8** — на более
новом интерпретаторе не заметили бы, что в скрипт заехала возможность языка, которой на
стенде нет.

## Жёсткие ограничения

- **Только стандартная библиотека Python 3.8+.** Зависимостей нет и не появляется: скилл
  работает в закрытых контурах, где `pip install` может быть недоступен.
- **Никакой сети и внешних сервисов** из скриптов.
- **Скрипты — обычные CLI.** Спрашивать пользователя они не могут: вопрос задаёт агент
  инструментом вопроса с вариантами. Скрипт может только сообщить, что чего-то не хватает,
  и вернуть ненулевой код.
- **Ничего не создаётся и не выполняется молча** — ни директория базы знаний, ни правка в
  коде, ни тикет во внешнем трекере. В интерактивном режиме это держится подтверждением
  пользователя; в автономном подтверждения у клиента **нет** — там границу держит среда
  запуска (изоляция процесса, сужение перечня MCP-серверов и инструментов правки), а
  инструкции скилла второй эшелон. Стенд без изоляции автономного режима не получает.
- **Автономный режим не догадывается.** Нет стенда, сервиса, источника логов или
  пригодного окружения — вердикт «данных недостаточно» с перечнем недостающего, а не
  значение по умолчанию. Отсутствие `report.json` означает несостоявшийся прогон и с этим
  вердиктом не путается.
- **Ограниченный режим не обходится.** Нет пригодного `python3` — разбор идёт по
  `references/limited-mode.md`, а уровень вывода не поднимается выше «гипотезы». Подбирать
  другой интерпретатор или писать парсер на ходу запрещено: тихо неверный разбор хуже
  честного «не могу».

## Соглашения в коде

- Точка входа скрипта — `run_script(main, __file__)` из `kb_common`: единая обработка
  выходов плюс телеметрия.
- «Сейчас» берётся из `now()`, а не из `datetime.now()`. Значение задаётся переменной
  `INCIDENT_NOW` и фиксируется на весь запуск: разбор, зависящий от дня прогона,
  невоспроизводим. Неразобранное значение — ошибка, а не тихий откат на системные часы.
- Вывод скрипта едет в контекст агента и остаётся там до конца разбора. Отсюда предел
  `MAX_SUMMARY_CHARS = 12000`; полный результат пишется в файл, а не в stdout.
- `INCIDENT_TRACE_FILE` — куда скрипты дописывают факт запуска. Значения аргументов туда
  не пишутся: на вход идут фрагменты логов и слова пользователя.
- Режим разбора берётся из `mode()` / `is_auto()`, а не выводится из окружения (наличия
  терминала, канала запуска, вида входного сообщения). Неизвестное значение
  `INCIDENT_MODE` — ошибка запуска: молча выбранный режим в автономном прогоне заметить
  некому.
- Значения в `report.json` кладут скрипты, а не модель. Всё, что уезжает в отчёт, проходит
  `scrub_text` — той же очисткой, что запись базы знаний.
- Путь к базе знаний разрешается только через `resolve_kb()` / `kb_dir()`, никогда не
  собирается на месте. Порядок и его обоснование — канон в
  `incident-detective/references/kb-format.md`, раздел «Где лежит база»; здесь не
  дублируется, чтобы копии не разошлись.
- Фильтры применяются **до** полного разбора записи, а не к разобранной: девять записей из
  десяти иначе разбираются, чтобы быть отброшенными.
- Вид записи базы читается через `kind_of()`: `incident` (разбор) или `source` (карта
  источников). Отсутствие поля `kind` — это `incident`, и так должно остаться: базы,
  созданные до появления карты, читаются как были. Поиск по инцидентам записи карты не
  возвращает и наоборот — смешивать виды в одной выдаче нельзя.

## Соглашения в текстах

- Всё по-русски: документация, комментарии, сообщения скриптов, тексты коммитов.
- Комментарий объясняет **почему**, а не пересказывает код. Причина, по которой сделано
  именно так, ценнее описания того, что и так видно.
- В `SKILL.md` и `references/` пишется то, что агент должен сделать, а не то, что скилл
  «умеет». Формулировки проверяются чтением — прогоном они не проверяются.

## README поддерживается в актуальном состоянии — всегда

`README.md` — единственный вход в проект для человека, который скилл ещё не видел, и
устаревает он молча: ни один прогон проверок не поймает, что раздел описывает то, чего
больше нет.

**Изменение не считается завершённым, пока README не приведён в соответствие.** Это часть
той же работы и того же коммита, а не отдельная задача «потом». Обязательно перечитай
README, если правка затрагивает:

- установку, перечень платформ, требования к окружению;
- состав скриптов или их флаги;
- перечень capability;
- числовые бюджеты и замеры;
- границы дозволенного скиллу;
- расположение и формат базы знаний.

Актуальность — не то же самое, что дописать раздел в конец. Если правка ничего из
перечисленного не меняет, README не трогается; если меняет — правится существующий
раздел, а не добавляется новый. Точка входа должна оставаться обозримой: подробность
длиннее нескольких абзацев уходит в `references/` или отдельный документ, а в README
остаётся ссылка.

Числовое утверждение в README называет инструмент, которым это число получается
(`tools/bench.py` для бюджетов) — иначе проверить его нечем.

То же правило относится к этому файлу: изменившиеся команды, ограничения и соглашения
обновляются здесь в том же изменении.

## Что проверками НЕ покрыто

Поведение модели: самозапуск скилла, порядок шагов разбора, формулировки в ответе. Это
инструкции в `SKILL.md`, и проверяются они чтением. Меняя их, не рассчитывай, что падение
теста поймает ошибку.

## Работа через OpenSpec

Изменения проходят через `openspec/`: предложение (`proposal.md`, `design.md`, дельта-спеки,
`tasks.md`) → реализация по задачам → синхронизация дельт в `openspec/specs/` → архив в
`openspec/changes/archive/`.

- Команды: `/opsx:explore`, `/opsx:propose`, `/opsx:update`, `/opsx:apply`, `/opsx:sync`,
  `/opsx:archive` — установлены все шесть.
- Несколько незавершённых предложений могут писать дельты в одну спеку — тогда порядок
  архивации важен, чтобы MODIFIED-блоки не затёрли друг друга.
- `openspec archive` повторно применяет дельты и падает на уже синхронизированной спеке.
  После ручной синхронизации директория переносится в `archive/` вручную.

## Границы скилла

Только диагностика. Никаких рестартов, деплоев и правок конфигов на стендах без явной
просьбы. Правки в код предлагаются, но не применяются молча. Тикет не заводится без показа
текста. Токены, пароли и персональные данные из логов в базу знаний и тикеты не попадают.

Сжатая версия; канон — раздел «Границы» в `incident-detective/SKILL.md`. Меняются границы
там, здесь только отражаются.
